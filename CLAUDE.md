# CLAUDE.md — WorkHelper, точка входа

> Это **точка входа**, а не свод правил. Здесь — то, что нужно в каждой задаче, и профиль
> проекта. Полные формулировки живут в `.ai/PROJECT_RULES.md` под ID (`K-\*`, `W-\*`, `F-\*`,
> `R-\*`, `T-\*`) и **не дублируются** здесь: ниже оперативные напоминания со ссылкой на ID.
>
> Правило меняется **только** в `.ai/PROJECT_RULES.md`. Если правки понадобились здесь и там
> одновременно — значит правило скопировано, и копию нужно убрать (урок T-106/T-107: два
> файла-близнеца по 26 КБ разошлись в двух местах и породили противоречия).

## Старт сессии

Загружать в порядке:

1. `.ai/TASK_REGISTRY.md` — **источник состояния**: активная задача, статусы, зависимости
   («что дальше»), плюс **протокол исполнения** (A0 → A1 → A2 → D → I → V)
2. `.ai/TECH_DEBT.md` — **источник рисков**: открытый долг, что требует действий владельца
3. `git status && git log --oneline -5` — состояние репозитория и последние изменения
4. `.ai/PROJECT_CHECKPOINT.md` — **журнал «почему»**, а не источник состояния. Читать
   **первые ~200 строк**: файл отсортирован «новое сверху», этого хватает на несколько
   последних задач. Целиком не читать — 150+ КБ не помещаются в одно чтение, и попытка даёт
   молча обрезанный результат. За конкретным старым решением идти `grep`-ом по заголовкам
   `## ` — по всему `.ai/`, включая `.ai/checkpoint-archive/`, куда вынесены старые записи
5. `.ai/PROJECT_RULES.md` — при любой задаче сложнее косметики; обязательно, если задача
   подпадает под триггер (значимый функционал, новая зависимость, багфикс, прод-баг,
   архитектурное изменение, работа с ПДн, новая модалка)

По необходимости: `.ai/ARCHITECTURE.md` (ADR), `.ai/SKELETON_FIRST_STANDARD.md`,
`.ai/POSTMORTEM_TEMPLATE.md`.

Планировать от состояния (пп. 1–3), а не от истории сообщений. Не цитировать правила —
ссылаться на ID.

> **Почему такой порядок** (T-501). Состояние проекта живёт в реестре задач и реестре долга
> в структурированном виде; чекпоинт пересказывает его прозой и ценен другим — он объясняет,
> **почему** сделано именно так. Раньше инструкция ставила чекпоинт первым и предписывала
> читать целиком — невыполнимое требование, из-за которого половина файла молча не доезжала.
>
> **Гигиена (по порогу, не по календарю):** когда `PROJECT_CHECKPOINT.md` превысит ~200 КБ,
> вынести **старую часть журнала** в `.ai/checkpoint-archive/<период>.md`, оставив в основном
> файле свежие записи и ссылку на архив. Отбор — по объёму, а не по возрасту: критерий
> «старше полугода» на проекте, которому несколько месяцев, не выбирал ни одной записи, то
> есть правило не могло сработать вовсе (TD-035, исправлено 2026-08-03; первый вынос сделан
> тогда же). Механизма нет — это ручная операция, и она редкая, а не обряд после каждой
> задачи: ритуал на каждой итерации в этом проекте уже отказывал (TD-027).
>
> **Чекпоинт — только журнал.** Держать в нём блоки «текущее состояние», «активная задача»,
> «оставшиеся задачи», «риски», «технический долг» запрещено: состояние живёт в
> `TASK_REGISTRY.md` и `TECH_DEBT.md`, а копия неизбежно расходится с ними (TD-035: такой
> блок пролежал в файле с июня и утверждал «фаза 0 завершена, активная задача T-101»).

## Ядро «всегда»

Правила, применимые в каждой задаче. Канонические формулировки — по ссылкам.

**Анализ.** Протокол исполнения обязателен в **каждой** задаче, а не только в крупных
(**K-44**): объём проходов пропорционален изменению, но пропуск этапа запрещён, а понижение
объёма записывается. Взятая в работу задача сначала проверяется на актуальность, и это
анализ не заменяет (**K-46**). Находка становится задачей только после A1 и отдельного A2
(**K-45**); в `.ai/TECH_DEBT.md` она попадает сразу, без ожидания анализа (**K-42**).

**Процесс.** Одна задача = одна ветка (**K-01**). Прямая работа в `main` запрещена без
исключений, merge только через PR (**K-02**) — защита ветки на GitHub не включена, правило
держится дисциплиной. Conventional Commits (**K-04**). Коммит только после локального
quality gate (**K-06**); упавшая проверка блокирует коммит до устранения **причины**
(**K-07**). Красный CI блокирует merge (**K-08**).

**Факты.** Не выдумывать API, библиотеки, результаты тестов и исследований (**K-10**). Не
сообщать о действиях, которые не выполнялись (**K-11**). Предположение помечать как
предположение (**K-13**). Не спрашивать то, что видно в коде, истории или документации
(**K-14**).

**Код.** Перед новым кодом изучить существующий и проверить переиспользование (**K-22**). Не
трогать несвязанные модули (**K-23**). Существующий паттерн важнее нового — consistency over
novelty (**K-38**).

**Безопасность.** Секреты — только в окружении, никогда в репозитории, коде или тексте
команд; приватные ключи и пароли заводит владелец, агент их не запрашивает (**K-33**).

**Честность документации.** Правило и документ не имеют права описывать механизм, которого
нет в репозитории; найденное расхождение фиксируется в `.ai/TECH_DEBT.md` немедленно
(**K-40**).

**Завершение.** Задача закрыта только по Definition of Done (**K-09**): тесты проходят,
регрессий нет, production build успешен, видимые изменения проверены на развёрнутом
окружении (**W-03**), чекпоинт обновлён. Признаки незавершённости — **K-32**.

## Как выполняется запрос

**Не задавать вопросов, ответ на которые есть в репозитории** (**K-14**). При неполных
требованиях: изучить существующую архитектуру → существующие паттерны → сопоставимые
реализации → выбрать наиболее консервативный согласованный вариант (**K-15**).

Конвейер каждого запроса:

| Фаза | Что делается |
|---|---|
| **1. Инспекция репозитория** | Архитектура, модули, маршруты, state management, слой данных, API-интеграции, права доступа, навигация, существующие тесты, дизайн-система. Определить затронутое; несвязанное не трогать (**K-23**) |
| **2. Функциональный анализ** | Что ожидается / что есть / чего нет / что сломано. Карта зависимостей, побочных эффектов и затронутых пользовательских сценариев |
| **3. Реализация** | Архитектурная согласованность, без дублирования, без временного кода, без TODO-заглушек, без моков, если они не запрошены явно. Только production-качество |
| **4. Предотвращение регрессий** | Проверить навигацию, переходы состояний, persistence, права, loading/error/empty, границы (**K-31**). Найденное чинить немедленно |
| **5. Тестирование и проверка развёртывания** | unit → integration → e2e → build → production build. При падении: первопричина → фикс → перезапуск затронутых и зависимых (**K-26**). Для видимых изменений — проверка на развёрнутом окружении (**W-03**) |

Формальный порядок этапов задачи (A0 актуальность → A1 анализ → A2 контр-анализ отдельным
проходом → D решение → I реализация → V верификация) — `.ai/TASK_REGISTRY.md §ПРОТОКОЛ
ИСПОЛНЕНИЯ ЗАДАЧИ`. Код пишется только на этапе I; обязательность и границы — **K-44**…**K-46**.

## Продукт

**Эталоны качества — референс, не объект копирования.** Jira, Linear, ClickUp, Asana,
Trello, Monday сверяются по качеству workflow, UX-паттернам, информационной архитектуре и
поведению управления задачами/спринтами/backlog. Если текущая реализация объективно слабее
проверенной индустриальной практики — улучшить. Интерфейсы не копировать, фичи не
дублировать бездумно.

**Доменные требования WorkHelper:**

- **Backlog** — отдельная логическая сущность, отдельный этап workflow и отдельный раздел
  интерфейса. Элементы backlog не отображаются в рабочих колонках доски до переноса в
  активный спринт.
- **Sprint Board** — только активные задачи спринта; колонки по статусам; корректные
  переходы; никаких backlog-элементов внутри доски.
- **Calendar** — привязка задач к датам, видимость дедлайнов, переход из календаря к задаче.
- **Notifications** — напоминания о дедлайнах и событиях, связь уведомлений с задачами.
- **Settings** — централизованная конфигурация с явной, обнаруживаемой точкой входа.

UI-правила — **F-01**…**F-04** (skeleton-first, прогрессивная загрузка, UX-проверка,
удаление мёртвого UI), React-правила — **R-01**, **R-02**.

## Уроки этого проекта

Куплены реальными инцидентами. Полные формулировки — `PROJECT_RULES §7`.

- **W-03 · «Смержено» ≠ «развёрнуто» ≠ «работает».** ТП-208 три недели считалась готовой, не
  работая у пользователя. Видимые изменения проверять на живом окружении со ссылкой.
- **W-06 · Молчаливый отказ недопустим.** Мониторинг не принимал события, деплой не
  доставлял код, бандл мог уйти в чужой backend — ни одного сообщения об ошибке. Либо
  fail-fast, либо безопасный дефолт. Экран, умеющий быть пустым, обязан отличать «пусто» от
  «не загрузилось».
- **W-07 · Сверять ветки перед выводом.** Готовая функциональность может быть просто не
  смержена — так «потерялись» 8 коммитов.
- **W-01/W-02 · Контракт фронтенд ↔ бэкенд.** Путь, метод и форма DTO проверяются
  end-to-end; 401/404 из UI — несогласованный контракт, а не «проблема авторизации».
- **W-08 · Расширение перечисления аддитивно.** Фронтенд деградирует к безопасному дефолту,
  а не бросает: маппер, бросавший исключение на новом типе задачи, обнулил целый экран.
- **W-04/W-05 · Валидаторы и права.** Бизнес-доступ — в сервисе, валидатор проверяет
  существование и формат. Проверять граничные роли и неактивные состояния сущностей.
- **K-34 · Гигиена ошибок.** Наружу — понятное сообщение, технические детали в логи.
- **R-02 · Router-хуки вне роутера** (прод-инцидент «белый экран», ТП-172): компоненты для
  NiceModal-модалок не используют `useNavigate`/`useRouter`.
- **R-01 · Error boundaries обязательны.** Краш блока ≠ белый экран приложения.
- **K-28 · Post-mortem прод-бага.** Сначала падающий тест, потом фикс; тест остаётся навсегда.

## Деплой

Прод — `https://wowoffcata.hlab.kz`. Деплой является частью поставки. **Владелец заранее
разрешил выкатывать без дополнительного подтверждения.**

Выкатывать самостоятельно: после мержа **скоупа задач** (не после каждого промежуточного
PR); **перед завершением сессии**, если в `main` остались смерженные, но не выкаченные
изменения — незадеплоенная работа не должна висеть до следующей сессии.

```bash
gh workflow run "Deploy to VDS" -f target=both
```

Дождаться прогона (`gh run watch`), убедиться, что изменение работает на **развёрнутом**
окружении (**W-03**), сообщить итог со ссылкой на прогон.

**Не выкатывать:** при красном CI; при известных незакрытых регрессиях; если пользователь
явно попросил не деплоить.

При неудачном деплое разобрать лог, устранить причину, повторить. Предыдущая сборка фронтенда
остаётся на сервере рядом в `*.old` — точка быстрого отката (**K-41**). Если workflow падает
на проверке секретов (`SERVER_IP`, `SERVER_USER`, `SSH_PRIVATE_KEY`) — сообщить владельцу:
секреты заводит только он (**K-33**).

## Профиль проекта

```
WorkHelper/
├── backend/     # Java 21 + Spring Boot 3.4 — REST API, бизнес-логика
├── frontend/    # React 19 + TypeScript + Vite — веб-интерфейс
├── mcp/         # MCP-сервер WorkTask (T-517): задачи и телеметрия, но НЕ правила (ADR-024)
├── docs/        # AsciiDoc, ER-диаграммы, диаграммы последовательностей
├── infra/       # nginx, GlitchTip
└── .ai/         # Инженерная память: правила, чекпоинт, задачи, долг, ADR
```

**Backend:** Java 21, Spring Boot 3.4.0, Spring Security + JWT, PostgreSQL + Liquibase,
Lombok, MapStruct, Swagger/OpenAPI.
**Frontend:** React 19, TypeScript, Vite, Material UI v7, TanStack Router/Query/Table,
Zustand, React Hook Form + Zod, Axios.

### Команды

| Операция | Команда |
|---|---|
| БД локально | `cp .env.example .env` и заполнить, затем `docker-compose up -d` — в `backend/enviroment/local` |
| Локальный профиль backend | `cp application-local.yml.example application-local.yml` в `backend/src/main/resources`, значения те же, что в `.env` |
| Тесты (backend) | `./gradlew test` — БД не требуется, тег `integration` исключён |
| Интеграционные тесты (backend) | `./gradlew integrationTest` — **нужен живой PostgreSQL и переменные** `IT_DB_URL`/`IT_DB_USER`/`IT_DB_PASSWORD` (дефолтов нет, без них задача останавливается с объяснением). БД поднимается одной командой: `docker run -d --name wt-it-pg -e POSTGRES_DB=worktask_ci -e POSTGRES_USER=worktask_ci -e POSTGRES_HOST_AUTH_METHOD=trust -p 5433:5432 postgres:16` — прогон локально занимает ~15 с и экономит круг через CI (проверено T-301) |
| Статический анализ (backend) | `./gradlew spotbugsMain` (входит в `build`; отчёт — `build/reports/spotbugs/main.html`) |
| Сборка (backend) | `./gradlew build` |
| Запуск (backend) | `./gradlew bootRun` |
| Установка (frontend) | `npm install` |
| Дев-сервер | `npm run dev` |
| Линт | `npm run lint` |
| Формат + автофикс | `npm run check` |
| Тесты (frontend) | `npm run test` |
| Production build | `npm run build` (`tsc -b && vite build`) |
| Генерация типов из OpenAPI | `npm run openapi-generate` |
| Проверка (MCP-сервер) | `npm run lint && npm test && npm run build` в `mcp/` |

> **Новый маршрут TanStack Router** требует регенерации `src/routeTree.gen.ts` (Vite-плагин
> `@tanstack/router-plugin` делает это при `npm run dev`/`build`). При ручной правке обновить
> все интерфейсы (`FileRoutesByFullPath`, `FileRoutesById`, `FileRouteTypes`,
> `*RouteChildren`), иначе TypeScript build упадёт.

> **Кириллица в пути репозитория** ломает classpath форкнутой JVM — backend-тесты падают
> все разом, включая нетронутые. Обходится прогоном копии из ASCII-пути.
