# Аудит фронтенда (T-201)

> Дата: 2026-08-08. Все числа получены измерением на этой дате, не оценкой.
> Цель — не «что сломано» (на это уже отвечали T-100 и quality audit), а **карта риска**,
> из которой T-202 берёт порядок работ.

---

## A0: описание задачи переписано

Исходный критерий T-201 — «Отчёт по состоянию компонентов: что работает, что нет» — написан
в фазе 2, когда состояние фронтенда действительно было неизвестно. С тех пор:

- T-100 прогнал пользовательские сценарии вживую и закрыл 8 багов (BUG-001…008);
- quality audit закрыл 13 дефектов UX и обработки ошибок (BUG-011…023);
- появились 622 теста в 94 файлах.

Вопрос «что не работает» больше не является открытым в прежнем виде: явные поломки
находились и чинились. **Открытым остаётся другое — где мы не узнаем о поломке**, потому что
там нет ни теста, ни обработки ошибки. Отчёт переписан под этот вопрос (**K-46**).

## 4. Разрыв: молчаливые отказы мутаций вернулись

Quality audit 2026-06-22 закрыл **BUG-014** — «все мутации без `onError` → ошибки API молча
игнорировались». В новом коде класс воспроизвёлся.

Проверено, а не предположено: в `QueryProvider` **нет** ни `MutationCache.onError`, ни
`defaultOptions.mutations`, то есть необработанное отклонение промиса не всплывает нигде.

| Хук | Мест вызова без обработки |
|---|---|
| `useProjectActions` | 3 из 4 |
| `useMeetings` | 1 из 3 |
| `useDeleteTask` | 1 из 3 |
| `useDeleteSprint` | 1 из 1 |
| `useTaskComments` | 1 из 1 |

**Итого не менее 7 мест вызова.** Число именно «не менее»: признаком обработки считалось
наличие `onError`/`try`/`catch` где-либо в файле вызывающего, поэтому файл с обработкой
*другой* мутации засчитан как благополучный. Реальное число может быть выше — уточняется
пофайловым разбором в рамках устранения.

Класс — **W-06**: операция не удалась, пользователь об этом не узнал. Удаление спринта и
удаление задачи в этом списке особенно неприятны: пользователь считает, что действие
выполнено.

## 5. Разрыв: fallback-и маскируют дрейф контракта

В мапперах `entities/*` отсутствующие поля бэкенда подменяются пустой строкой:

```
entities/task/mapDTO.ts:24    code: taskDTO.code || ''
entities/task/mapDTO.ts:53    sprintId: task.sprintId || ''
entities/task/mapDTO.ts:69    lastName: user.lastName || ''
entities/sprint/mapDTO.ts:19  name: sprint.name ?? ''
entities/user/mapDTO.ts:8     // TODO: исправить `|| ''` когда бекенд поправит типы
```

Это ровно механизм, из-за которого TD-031 оказался достижим: `mapProjectDtoToProjectInfo`
превращал **отсутствующее** поле в `[]`, и расхождение контракта выглядело как пустые данные
(**W-08**). Пустая строка вместо кода задачи не падает — она делает задачу неоткрываемой
по ссылке, и это не отличимо от «задачи нет».

Отдельно: `TaskCard.styles.ts` и три маппера несут **26 маркеров** `TODO`/`FIXME`, из них
четыре прямо описывают несогласованность типов с бэкендом.

## 6. Что из этого следует для T-202

Порядок покрытия — по цене отказа, а не по удобству:

1. **`widget/Board`** — центральный экран, 654 строки, 0 тестов, исторический источник
   четырёх багов. Начинать здесь.
2. **Мутации без обработки ошибок** — это не тест, а фикс; тест закрепляет его (**K-28**).
3. **`page/auth` и `routes/_auth`** — отказ входа делает недоступным всё остальное.
4. **`widget/DashboardLayout`** — сайдбар и уведомления, каркас каждой страницы.
5. **`features/sprint` и `widget/Sprint`** — 8 компонентов, ноль тестов, и это половина
   доменного цикла продукта.

`features/voice` в список не входит: он покрыт лучше всех остальных вместе взятых.

## 7. Граница доказуемости

Всё выше получено **статическим измерением репозитория**. Не проверялось:

- поведение на живом окружении — требует входа, пароли агент не вводит (**K-33**);
- фактическое покрытие в процентах — coverage-провайдер в проекте не подключён
  (`PROJECT_RULES §Механизмы, которых нет`), поэтому «94 файла тестов» и «622 теста» — это
  объём, а не покрытие;
- утверждение «обработки ошибки нет» проверено на уровне файла, а не конкретного вызова —
  см. оговорку в §4.
