# Разбор текущего набора правил по уровням переносимости

> Дата: 2026-07-28. Источники разбора: `CLAUDE.md` (26.7 КБ) и `.ai/PROJECT_RULES.md` (26.1 КБ),
> плюс `.ai/SKELETON_FIRST_STANDARD.md` (4.2 КБ) и `.ai/POSTMORTEM_TEMPLATE.md` (3.7 КБ).
> Цель — получить переносимое ядро правил и увидеть дубли.
> Ничего не удалено и не изменено: это разбор, а не рефакторинг.

## Обозначения

**Уровень:** `0` — становится функцией платформы (перестаёт быть текстом) · `ЯДРО` — переносится
в любой проект · `ПАК` — переносится в проекты того же класса · `ПРОФИЛЬ` — принадлежит
конкретному проекту.

**Тип:** принцип (как думать) · гейт (что истинно, чтобы двигаться дальше) · процедура
(последовательность) · запрет.

**Сила:** MUST / SHOULD.

**Проверка:** авто (машиной) · полуавто · ручная.

**Когда:** триггер загрузки. `всегда` — попадает в каждую задачу; остальные — по условию.

## 2. Уровень 0 — перестаёт быть правилом, становится функцией платформы

Эти пункты сейчас написаны текстом, потому что у агента нет системы, которая бы их держала.
Как только проект живёт в WorkTask, текст не нужен — работает продукт.

| Что сейчас | Во что превращается |
|---|---|
| `CONTEXT LOADING ORDER` — порядок чтения файлов при старте | Контекст-бандл под задачу |
| `TOKEN ECONOMY` — «не цитировать правила, ссылаться» | Следствие бандла; правило исчезает |
| `TASK MANAGEMENT` — реестр задач в файле, статусы `NOT_STARTED…` | Задачи и статусы доски в WorkTask |
| `PROJECT CHECKPOINT` — файл прогресса | Состояние проекта в WorkTask |
| `TECHNICAL DEBT` — реестр в `.ai/TECH_DEBT.md` | Раздел техдолга проекта |
| `AUTONOMOUS EXECUTION MODE` — что можно без подтверждения | Настройка проекта «уровень автономии» |

## 6. Балласт — кандидаты на удаление

Критерий: агент знает это и без правила, либо это невозможно проверить, либо это дублирует
то, что видно в репозитории. Каждая строка сейчас оплачивается токенами при каждом запуске.

| Что | Почему кандидат на удаление |
|---|---|
| `CODE QUALITY` — перечисление SOLID, DRY, KISS, YAGNI, Clean Architecture, SoC, DI | Модель это знает. Ценность появляется только если у проекта есть **отклонение** от общепринятого — тогда пишем отклонение, а не список аббревиатур |
| «Композиция вместо наследования», «читаемость вместо преждевременной оптимизации» | То же самое |
| `SYSTEM MODE` — перечисление ролей (Principal Architect, QA, DevOps, Security…) | Ролевое заклинание, непроверяемо; полезность даёт неочевидная информация, а не назначение ролей |
| `FINAL OBJECTIVE` / `PRIMARY OBJECTIVE` | Декларация намерений; не содержит проверяемого требования. Дублирует Definition of Done |
| `PRODUCT STRUCTURE` — описание дерева каталогов | Дублирует репозиторий: агент видит дерево. Оставить только команды (уходят в профиль) |
| Приложение «Согласованность правил» (таблица разрешения кажущихся конфликтов) | Существует только потому, что правила дублируются в двух файлах. При нормализации исчезает вместе с причиной |

## 7. Найденные дубли и конфликты

### Дубли между `CLAUDE.md` и `PROJECT_RULES.md`

Почти полностью дублируются: SYSTEM MODE, SOURCE OF TRUTH, RESEARCH FIRST,
ANTI-HALLUCINATION, TASK MANAGEMENT, PROJECT CHECKPOINT, GIT WORKFLOW, COMMIT POLICY,
TESTING, TEST COVERAGE, CI/CD, CODE QUALITY, SECURITY, DOCUMENTATION, ROLLBACK STRATEGY,
DEFINITION OF DONE, FINAL/PRIMARY OBJECTIVE — **17 блоков**.

При этом `CLAUDE.md` загружается автоматически, а `PROJECT_RULES.md` — по инструкции
`CONTEXT LOADING ORDER` из самого же `CLAUDE.md`. То есть корпус оплачивается **дважды
при каждом старте сессии**.

### Реальные противоречия

| # | Противоречие | Где |
|---|---|---|
| 1 | Покрытие: «целевой ориентир 80%, **не блокирующий gate**» против «минимальное покрытие ≥80%, **порог проверяется в сборке/CI**» | `CLAUDE.md` §TEST COVERAGE ↔ `PROJECT_RULES.md` §TESTING POLICY |
| 2 | `main`: «запрещено коммитить напрямую, **единственное исключение — критический hotfix** с уведомлением» против «запрещено работать напрямую в `main`» без исключений | `CLAUDE.md` §GITHUB WORKFLOW ↔ `PROJECT_RULES.md` §GIT WORKFLOW |

Оба противоречия — прямое следствие дублирования: одна и та же норма записана дважды и
разошлась при правках. Это и есть аргумент за «правило формулируется один раз».

### Формально не конфликт, но требует внимания

`AUTONOMOUS EXECUTION MODE` («не запрашивать подтверждения», «автоматически переходить к
следующей задаче») задаёт уровень автономии, который может расходиться с ожиданиями
пользователя в конкретной сессии. В платформе это должно стать **настройкой проекта**,
а не правилом в тексте.

---

## 8. Что из этого следует

1. **Ядро существует.** 36 правил переносятся в проект на любом стеке без единой правки —
   при условии, что команды вынесены в контракт возможностей.
2. **Дубль — главный источник расхода и расхождений.** Два файла по 26 КБ, 17 общих блоков,
   два разошедшихся правила.
3. **Часть правил не должна быть текстом.** 8 блоков превращаются в функции платформы,
   включая самый дорогой — чекпоинт на 128 КБ.
4. **Триггеры важнее объёма.** Из 36 правил ядра только 12 нужны в каждой задаче.
   Остальные — по условию.
5. **Уроки проекта — самая ценная часть.** W-01…W-05, R-01, R-02, T-02 куплены реальными
   инцидентами. Именно они дают ту «неочевидную информацию», ради которой правила и нужны.
