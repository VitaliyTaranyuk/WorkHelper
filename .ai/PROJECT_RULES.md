> содержит ядро «всегда» и профиль проекта, а на остальное ссылается сюда по ID.
> Одно правило = одна формулировка = один ID. Дублировать текст правил запрещено.

## Как пользоваться реестром

**Уровень** — переносимость правила: `ЯДРО` переносится в любой проект · `ПАК` — в проекты
того же класса (клиент-сервер, фронтенд, React, тесты) · `ПРОФИЛЬ` — принадлежит WorkHelper.

**Триггер** — когда правило применяется. `всегда` — в каждой задаче (эти правила
продублированы **по смыслу, но не по тексту** в `CLAUDE.md`: там оперативная формулировка,
здесь — каноническая с ID). Остальные — по условию; читать по мере попадания в условие.

**Сила** — `MUST` (нарушение блокирует завершение) · `SHOULD` (отклонение допустимо с
обоснованием).

**Проверка** — `авто` (машиной в CI/сборке) · `полуавто` · `ручная`.

> Если правило заявляет автоматическую проверку — механизм обязан существовать в
> репозитории. Это отдельное требование, см. **K-40**; расхождения устранены T-106.

## ОПРЕДЕЛЕНИЯ (глоссарий)

Термины, используемые в правилах как пороги и условия:

- **Значимый функционал** — изменение, затрагивающее доменную модель, публичный API или
  пользовательский сценарий. Не косметика и не рефакторинг без смены поведения.
- **Критическая бизнес-логика** — доменные операции и сервисы, влияющие на данные
  пользователя, доступ, расчёты или интеграции.
- **Блокирующий дефект** — дефект уровня `CRITICAL` или `HIGH` (критерии — **K-29**).
- **Production-ready** — состояние, удовлетворяющее **K-09** (Definition of Done) при
  отсутствии блокирующих дефектов.
- **Развёрнутое окружение** — `https://wowoffcata.hlab.kz`. «Собралось локально» им не является.

| **K-09** | Definition of Done (§Definition of Done) выполнен целиком | гейт | MUST | завершение | полуавто |

### Quality gate — канонический список проверок перед коммитом

Порядок фиксированный; список ссылается на профиль проекта (`CLAUDE.md §Команды`):

1. Форматирование
2. Линтеры
3. Статический анализ *(в проекте отсутствует — T-104; до тех пор шаг пропускается осознанно)*
4. Unit-тесты
5. Integration-тесты *(в проекте отсутствуют — T-101)*
6. UI / E2E-тесты *(в проекте отсутствуют — T-203/TD-014)*
7. Build validation, включая production build

> Шаги 3, 5, 6 помечены отсутствующими намеренно: правило не имеет права требовать запуска
> того, чего в репозитории нет (**K-40**). По мере закрытия задач пометки снимаются.

### Definition of Done

Задача получает `COMPLETED`, только если истинны **все** условия:

- [ ] Код реализован, архитектура осталась когерентной
- [ ] Тесты написаны и проходят (**K-24**, **K-25**)
- [ ] Регрессий нет; затронутые сценарии проверены (**K-31**)
- [ ] Build и production build успешны
- [ ] Для изменений, видимых в приложении, — проверено на развёрнутом окружении (**W-03**)
- [ ] Документация обновлена и соответствует реальности (**K-40**)
- [ ] Коммит выполнен после quality gate (**K-06**)
- [ ] `.ai/PROJECT_CHECKPOINT.md` обновлён
- [ ] Pull Request создан
- [ ] Блокирующих дефектов нет

Пока хотя бы одно условие ложно — работа продолжается. Признаки незавершённости — **K-32**.

## 4. ЯДРО — качество и тестирование

| ID | Правило | Тип | Сила | Триггер | Проверка |
|---|---|---|---|---|---|
| **K-24** | Тесты пишутся до или одновременно с кодом | процедура | SHOULD | реализация | ручная |
| **K-25** | Критическая бизнес-логика имеет тестовое покрытие. Ориентир — 80% line coverage; это ориентир качества, **не блокирующий гейт**: приоритет у критичных путей и негативных сценариев, а не у «дотягивания процента» тестами на тривиальный код | гейт | MUST | реализация | ручная |
| **K-26** | Не останавливаться на первой ошибке: найти первопричину, исправить, перезапустить затронутые **и зависимые** тесты. Никогда не отмечать работу завершённой при падающих тестах | процедура | MUST | падение тестов | ручная |
| **K-27** | Ошибка исправляется через первопричину: найти причину → исправить причину → добавить тест → проверить соседние компоненты | процедура | MUST | багфикс | ручная |
| **K-28** | Сбежавший в прод баг сначала воспроизводится **падающим** тестом, затем чинится; тест остаётся навсегда. Шаблон и реестр — `.ai/POSTMORTEM_TEMPLATE.md` | процедура | MUST | прод-баг | полуавто |
| **K-29** | Дефект получает уровень: `CRITICAL` (недоступен ключевой сценарий, потеря/повреждение данных, брешь в безопасности — чинить немедленно, блокирует релиз) · `HIGH` (основной сценарий работает некорректно, обходного пути нет — чинить до новых функций) · `MEDIUM` (есть обходной путь — планово) · `LOW` (косметика). Все `CRITICAL` и `HIGH` устраняются до разработки новых функций | процедура | MUST | багфикс | ручная |
| **K-30** | Самопроверка до завершения: архитектура, код, безопасность, производительность, тесты. Найденное устраняется **до** коммита | процедура | MUST | завершение | ручная |
| **K-31** | Перед завершением проверить затронутые сценарии: навигацию, переходы состояний, persistence, права доступа, состояния loading/error/empty, граничные случаи. Найденные регрессии исправлять немедленно | процедура | MUST | завершение | ручная |
| **K-32** | Признаки незавершённости — работа не может быть закрыта, если есть хотя бы один: сломанная навигация, недоступная функциональность, мёртвые кнопки, разорванные сценарии, несогласованные состояния, необработанные ошибки, отсутствующая валидация, отсутствующий persistence, падающие тесты | гейт | MUST | завершение | ручная |

**Проектные конвенции тестирования** (уровень ПРОФИЛЬ): JUnit 5 + Mockito на backend,
Vitest на frontend; `@ExtendWith(MockitoExtension.class)` — строгий режим стабов; фикстуры
в `TestFixtures.java`, без Mockito-стабов в `@BeforeEach`.

**Измерение покрытия отсутствует:** JaCoCo не подключён, coverage-провайдер Vitest не
установлен, шага покрытия нет ни в одном workflow. **K-25** оценивается ревью. Подключение — T-105.

## 8. Процедуры (раскрывают правила, не повторяют их)

### Задачи и прогресс

`.ai/TASK_REGISTRY.md` — реестр: ID, название, описание, зависимости, статус, критерии
завершения. Статусы: `NOT_STARTED` · `IN_PROGRESS` · `COMPLETED` · `BLOCKED`. Большие задачи
разбиваются на подзадачи. Статус `COMPLETED` присваивается только по **K-09**.

`.ai/PROJECT_CHECKPOINT.md` обновляется после каждой завершённой задачи: прогресс,
завершённые задачи, активная задача, оставшиеся задачи, риски, технический долг, последние
изменения, следующие шаги. При возобновлении работы планировать от последнего чекпоинта, а
не от истории сообщений. Задачи со статусом `COMPLETED` не повторять.

**Протокол исполнения задачи** (A1 → A2 → D → I → V) — в `.ai/TASK_REGISTRY.md`; код
пишется только на этапе I.

### Автономность

Работать автономно, переходя к следующей задаче реестра без ручного апрува. **Не запрашивать
подтверждения** для: создания и изменения файлов, удаления неиспользуемого кода,
рефакторинга, запуска тестов/линтеров/сборки, создания веток и коммитов, деплоя по
§Deployment (`CLAUDE.md`).

**Остановиться и спросить, только если:** требуется продуктовое решение; есть несколько
равнозначных архитектурных вариантов; возникла блокирующая техническая проблема;
отсутствует доступ к внешней системе.

> Автономность = отсутствие ручного апрува. Она **не отменяет** гейтов **K-06**, **K-08**,
> **K-09** и запрета **K-02**.

### Экономия контекста

Не цитировать и не пересказывать правила — ссылаться на ID (`см. K-27`) или секцию
(`PROJECT_RULES §Quality gate`). Долговременные инструкции живут в `.ai/`, а не в переписке;
новая постоянная политика фиксируется файлом, а не сообщением.

### CI/CD — фактический состав

Конфигурация: `.github/workflows/`. PR обязан проходить все проверки, которые пайплайн
**реально выполняет**:

| Проверка | Backend (`backend-ci.yml`) | Frontend (`frontend-ci.yml`) |
|---|---|---|
| Lint | — | `npm run lint` |
| Unit-тесты | `./gradlew test` | `npm run test` |
| Build validation | `./gradlew build -x test` | `npm run build` |

Отсутствует в пайплайне (до закрытия задачи проверка считается ручной): статический анализ
(T-104) · интеграционные тесты (T-101) · dependency security scan (T-303) · lint и формат на
backend (задача не заведена).

> `backend-ci.yml` поднимает сервис `postgres:16`, которым **не пользуется ни один тест** —
> он заведён авансом под T-101.

практики, проверенные open-source решения, автоматизированное тестирование, контроль

CI зелёный; архитектура документирована; изменения развёрнуты и проверены на живом
окружении; проект готов к следующему этапу.
