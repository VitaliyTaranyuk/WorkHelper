## Завершено 2026-07-28: T-501 — аудит доставки правил: заявленный канал сломан, крупнейший не описан

Результат — `.ai/RULES_DELIVERY_AUDIT.md`. Кода задача не касалась.

**Правила доходят пятью каналами, и файловый — не самый объёмный:**

| Канал | Объём | Надёжность |
|---|---|---|
| `CLAUDE.md` (автоматически) | 15.7 КБ | высокая |
| `.ai/*.md` по инструкции | 223 КБ | **средняя — см. ниже** |

**Заявленный канал физически не выполняется.** `CLAUDE.md` предписывает первым делом
прочитать `PROJECT_CHECKPOINT.md` — а он вырос до **152.7 КБ / 1686 строк / 74 секции** и не

растёт монотонно: 121 КБ (27.07) → 152 КБ (28.07), **+31 КБ за два дня**, и занимает **64%**
стартового контекста — при том что на старте из него нужны четыре вещи: активная задача,
последние изменения, риски, следующие шаги.

**Крупнейший канал не описан нигде.** 762 комментария вида «ТП-176: форма списка спринтов
проверяется на границе — сломанный ответ даёт error-состояние, а не краш доски» — это самый
эффективный вид доставки: правило приезжает вместе с кодом, который собираются менять, и
объясняет, почему здесь сделано именно так. Ни `CLAUDE.md`, ни `PROJECT_RULES.md`, ни
`RULES_TAXONOMY.md` его не упоминают.

**Правила привязаны к одному вендору:** ни `AGENTS.md`, ни `.cursorrules`, ни
`copilot-instructions.md` — ничего. Смена агента = потеря инженерной памяти (обоснование
T-514).

**Что должно стать данными:** чекпоинт (состояние + журнал), реестр задач (уже дублирует
доску WorkTask и синхронизируется вручную), техдолг, реестр правил. Важное следствие: T-107
уже привёл правила к табличному виду с полями — **миграция «правила → данные» не требует
переосмысления, только переноса**. Но крупнейший выигрыш даёт не она, а чекпоинт: 152 КБ →
четыре поля на старте.

**Рекомендация, не дожидаясь платформы:** разрезать чекпоинт на активную часть и архив по
месяцам. Снимает ~130 КБ со старта и чинит инструкцию, которая сейчас предписывает
невозможное — то есть требуется по **K-40** независимо от Фазы 5.

## Завершено 2026-07-28: T-500 — аудит мультипроектности: разрыв ровно один, но корневой

Результат — `.ai/MULTIPROJECT_AUDIT.md`. Кода задача не касалась.

**Хорошая новость: модель уже мультипроектная.** Изоляция данных на бэкенде корректна —
`Project` разделяет задачи, спринты, статусы, встречи и права; каждый проектный запрос
проверяет членство через `CheckerUtil`; назначить исполнителем не-участника нельзя; ключи
React Query содержат `projectId`, протечки кэша между проектами нет. Девять областей
работают на N проектов без единой правки.

**Разрыв — не в модели, а в способе выбора проекта.** «Текущий проект» это не параметр
URL, а серверное поле `User.last_project_id`, которое переписывает **обычный GET**:
`ProjectsService.getProjectData` (`:135`) на каждое чтение данных проекта делает
`setLastProjectId` + `flush`. Фронтенд опирается на этот побочный эффект как на механизм —
«переключение проекта» реализовано как мутация, вызывающая тот же `GET /projects/{id}`.

Из одного этого решения вытекает большинство найденного:

| # | Разрыв |
|---|---|
| G-1/G-2/G-3 | Проект живёт на сервере, а не в URL. Доска `/main` — единственный раздел без `projectId`, то есть не deep-link. Две вкладки с разными проектами невозможны: списки опрашиваются каждые 15 с и первая вкладка уедет за второй. Открытие бэклога другого проекта молча меняет текущий проект |
| G-4/G-5 | `/task/$code` резолвится в текущем проекте, а `Project.code` (префикс кодов) **не имеет ограничения уникальности ни в БД, ни в сервисе** — два проекта могут иметь префикс `ТП`, и `ТП-236` будет существовать в обоих |
| G-6 | Уведомление хранит `projectId` и использует его для встреч, но задачу открывает только по коду — уведомление из другого проекта даст 404 |
| G-8/G-9 | `last_project_id` не сбрасывается при удалении проекта (пользователь остаётся «в» удалённом); открытая карточка задачи переживает переключение проекта |

**Отдельно от Фазы 5, актуально уже сейчас — TD-028:** `GET /users/picker` отдаёт **всех
пользователей системы вместе с email**, а не участников проекта, вопреки собственному
комментарию. Это расходится с K-36 (ПДн) и даёт мёртвый выбор в UI: не-участника видно в
списке, но назначить его бэкенд не даст.

**Граница доказательности зафиксирована честно.** У владельца ровно один проект (проверено
вживую), поэтому все мультипроектные сценарии **выведены из кода и не воспроизводились** —
второго проекта не существует, а заводить его в боевых данных ради эксперимента я не стал.
Каждый пункт аудита помечен «проверено вживую» либо «выведено из кода». Именно «один
проект» и маскировал эти разрывы всё время.

**Вход для следующих задач:** порядок работ в T-518 уточнён — снятие побочного эффекта с
`GET /projects/{id}` и перевод доски на `projectId` в маршруте закрывают четыре разрыва
разом; оба пункта архитектурные (K-37) и требуют ADR в T-503. Три вопроса вынесены владельцу
(архивный проект в переключателе, область уникальности префикса кодов, нужно ли вообще
серверное «последний проект»).

## Завершено 2026-07-28: T-107 — правило теперь формулируется один раз

T-106 закрыл симптом (правила врали про механизмы), T-107 — причину. Причиной был дубль:
`CLAUDE.md` (30.9 КБ) и `.ai/PROJECT_RULES.md` (28.5 КБ) пересекались по 17 блокам, при этом
первый загружается автоматически, а второй — по инструкции из него же. Корпус оплачивался
дважды на каждом старте, а одна и та же норма, записанная в двух местах, разошлась при
правках — так и появились противоречия T-106.

**Что нашёл контр-анализ.** Карта дублей из A1 считала блоки одинаковыми по названию, но по
смыслу они разошлись: `§TESTING FIRST` требовал Integration/UI/E2E без оговорок, а
`§QUALITY GATE` — те же проверки с пометкой «если применимо». Механическое слияние незаметно
ужесточило бы одно требование или ослабило другое, то есть воспроизвело бы ровно тот дефект,
который задача закрывает.

**Решение — разделить по триггеру загрузки, а не держать два близнеца:**

| Файл | Роль | Объём |
|---|---|---|
| `CLAUDE.md` | Точка входа: старт сессии, ядро «всегда», конвейер запроса, продуктовые требования, уроки проекта, деплой, профиль (стек и команды) | **15.7 КБ** (было 30.9) |
| `.ai/PROJECT_RULES.md` | Реестр 59 правил: ID, уровень (ЯДРО/ПАК/ПРОФИЛЬ), сила (MUST/SHOULD), триггер, способ проверки. Грузится по условию | 34.6 КБ |

Каждая формулировка существует **ровно в одном месте**: точка входа ссылается по ID
(`K-27`, `W-03`, `F-01`…) и текст правил не копирует. Точка входа при этом самодостаточна —
работает, даже если реестр не загружен: это защита от регрессии «правила есть, но их никто
не прочитал». Проверяемость закреплена картой «правило → где сформулировано»
(`PROJECT_RULES §9`) и инструкцией, куда класть новое правило.

**Удалённый балласт** (обоснование — `RULES_TAXONOMY §6`): перечисление ролей `SYSTEM MODE`,
дублирующий `PRIMARY OBJECTIVE`, приложение «согласованность правил» (существовало только
из-за дубля — уцелевшее разрешение K-16 ↔ K-17 сохранено примечанием), описание дерева
каталогов как правила.

**Уроки проекта не сокращены, а систематизированы:** девять «Lessons enforced» превратились
в пак `W-01…W-08` + `R-01/R-02` с триггерами, и к ним добавлены два, выведенные из свежих
инцидентов, — **W-06** (молчаливый отказ недопустим: половина закрытого в июле долга
отказывала беззвучно) и **W-08** (расширение перечисления на бэкенде аддитивно, фронтенд
деградирует к дефолту, а не бросает — иначе обнуляется целый экран).

**Проверка:** 0 дубликатов ID; 0 битых ссылок (26 из точки входа, 59 внутри реестра); 38
контрольных требований из старых файлов сверены автоматически — все на месте. Экономия на
старте сессии: 15.7 КБ вместо 59.3 КБ, если реестр не понадобился по триггеру.

## Завершено 2026-07-28: T-106 — правила перестали описывать несуществующие механизмы

Набор правил утверждал наличие проверок, которых в репозитории нет. Опасность не
теоретическая: правило, ссылающееся на несуществующий гейт, создаёт ложное чувство
защищённости — «покрытие проверяется в CI» читается как «за этим следит машина», хотя
не следит никто.

**Закрыто четыре расхождения** (три из постановки + одно, найденное контр-анализом):

| # | Правило утверждало | Реальность |
|---|---|---|
| 1 | «Порог покрытия ≥80% проверяется в сборке/CI (JaCoCo / Vitest c8)» | JaCoCo не подключён, coverage-провайдер Vitest не установлен, шага покрытия нет ни в одном workflow |
| 2 | `CLAUDE.md` допускал прямой коммит в `main` для «критического hotfix»; `PROJECT_RULES.md` запрещал без исключений | Защита ветки не включена (`Branch not protected`), но за 214 merge-коммитов исключение не использовалось ни разу |
| 3 | «Обязательные проверки: Lint · Static Analysis · Unit · Integration · Build · Security Scan» | Фактически backend = build + unit; frontend = lint + unit + build |
| 4 | **(найдено A2)** Integration Tests в том же обязательном списке | Не существует ни одного теста с `@SpringBootTest`/Testcontainers на 23 тестовых класса — при том что `backend-ci.yml` поднимает `postgres:16`, которым не пользуется никто |

**Принцип правки — разделить намерение и механизм.** Ни одно требование не ослаблено:
что было MUST, осталось MUST. Менялись только утверждения о том, **чем** требование
обеспечено. Где механизма нет, правило это признаёт и ссылается на задачу, которая его
заводит (T-101 интеграционные тесты, T-102 защита ветки, T-104 статанализ, T-105
покрытие, T-303 security scan). Исключение «критический hotfix» удалено как мёртвая
норма: даже активная уязвимость прода (TD-019) и три недели починки деплоя (TD-021)
прошли через PR.

**Что дал контр-анализ отдельным проходом.** Кроме четвёртого расхождения — сплошная
проверка остальных механизмов, упомянутых в правилах: `TestFixtures.java`, гейт
`console.error` в `src/test/setup.ts`, `ErrorBoundary`, `defaultErrorComponent`,
`TaskCardSkeleton`, `openapi-generate`, `infra/nginx-vds.conf`, workflow `Deploy to VDS`
с входом `target` — все существуют, гипотезы отвергнуты.

**Побочные находки, зафиксированы немедленно:**
- **TD-027 (новый).** Локальный quality gate не автоматизирован ничем: `frontend/lefthook.yml`
  объявляет `pre-commit → lint` и `pre-push → build`, но хуки не установлены — в
  `.git/hooks` только `prepare-commit-msg`, которого в конфиге нет, lefthook недоступен
  (`Can't find lefthook in PATH`), `prepare`-скрипта нет. Обнаружено буквально на
  собственном коммите этой сессии.
- **TD-003 переформулирован.** Долг не в «прямых push в `main`» (их нет с 21.06.2026), а
  в отсутствии защиты ветки как механизма. Устраняется **владельцем** (T-102).

Проверка: изменения только в тексте правил + один комментарий в `backend-ci.yml`; все три
workflow структурно валидны, каждое внесённое фактическое утверждение перепроверено
первичным источником (одна неточность — «24 тестовых класса» вместо 23 — найдена и

## Завершено 2026-07-28: TD-021 закрыт — деплой впервые доехал до прода автоматически

Три недели «смержено ≠ развёрнуто» закончились: `Deploy to VDS` отработал
целиком (сборка → выкладка → проверка, что сайт отвечает 200) и выложил фикс
списка задач.

**Что мешало и как решено.** Workflow умел только вход по ключу, а владельцу
этот путь не дался: приватный ключ многострочный, и при заливке в секрет через
PowerShell-пайп переносы строк портятся — Actions получал значение, которое
OpenSSH не разбирает (`error in libcrypto`). Дальше три итерации, каждая
закрыла отдельный класс ловушек:

| PR | Проблема | Решение |
|---|---|---|
| #196 | Единственный способ входа — ключ | Ключ ИЛИ пароль; способ выбирается один раз, шаги используют `$SSH`/`$SCP` |
| #197 | Пароль из `gh secret set` приезжает с хвостовым `\n`, сервер его отвергает | Обёртка срезает `\r\n` в момент запуска (пароль не копируется в `GITHUB_ENV` и не попадает в `argv`) |
| #198 | `PreferredAuthentications=password` отклоняется серверами с PAM | Разрешён `keyboard-interactive` (первым), `NumberOfPasswordPrompts=1` |

**Общий урок этих трёх.** Все три отказа выглядели в логе ОДИНАКОВО —
`Permission denied`, неотличимо от неверного пароля, при том что тот же пароль
руками проходил. Значение секрета маскировано, поэтому отличить «не тот
пароль» от «не тот метод аутентификации» по логу невозможно в принципе.
Диагностика двигалась только за счёт того, что каждая гипотеза проверялась
отдельно и отсекалась (владелец подтвердил пароль вручную → дело не в нём).

**Приоритет остаётся за ключом:** если завести `SSH_PRIVATE_KEY`, workflow
переключится на него без правок. Пароль — сознательный компромисс: он даёт
полный доступ к учётной записи и не отзывается точечно.

**Политика деплоя** зафиксирована в `CLAUDE.md` (раздел `DEPLOYMENT POLICY`,
PR #195): агент выкатывает сам после мержа скоупа задач и перед завершением
сессии, если в `main` осталось невыкаченное.

## Исправлено 2026-07-28: BUG «в списке задач остались только завершённые» (ветка `claude/workhelper-missing-tasks-backlog-1ac14c`)

Пользователь сообщил: в «Списке задач» видна одна секция «Завершённые» —
активный спринт и Бэклог пропали. Подтверждено вживую на проде под
`test2@mail.ru`: API отдаёт 30 задач (7 в активном спринте, 23 в бэклоге),
фронт не показывает ни одной секции.

**Корень (не данные и не бэкенд).** Бэкенд знает четыре типа задач
(`BUG|TASK|RESEARCH|STORY`) и четыре приоритета (`BLOCKER|HIGH|MEDIUM|LOW`) —
перечисления существуют с первого коммита. Фронт знал два типа и три
приоритета, а `castTaskType`/`castTaskPriority` на всём остальном **бросали
исключение**. В бэклоге появились 5 задач с типом `RESEARCH` (заведены через
API) — маппинг падал, `Promise` запроса `sprint-list` уходил в reject,
`sortedSprints` оставался пустым, и страница молча рисовала одну секцию
«Завершённые» (она грузится отдельным запросом — отсюда иллюзия «остались
только завершённые»). Доска уцелела случайно: в активном спринте
задач-исследований не было.

**Что сделано (устранён класс, а не случай):**
- **Типы фронта = перечисления бэкенда.** `TaskType` += `RESEARCH|STORY`,
  `TaskPriority` += `BLOCKER`; представление типа (иконка + подпись) вынесено
  в единый `entities/task/typeMeta` — раньше оно дублировалось в трёх местах,
  поэтому добавление типа не было сделано ни разу.
- **Мапперы не бросают.** Неизвестное значение деградирует до безопасного
  дефолта (`TASK`/`MEDIUM`) и уходит в прод-мониторинг как дрейф контракта
  (одно событие на значение, без флуда). Расширение перечисления на бэкенде —
  аддитивное изменение, оно не имеет права обнулять экран.
- **Честное error-состояние.** «Список задач» и доска показывают
  «не удалось загрузить» + «Повторить» (`shared/ui/components/LoadErrorState`)
  вместо пустоты: экран, который умеет быть пустым, обязан отличать «пусто»
  от «не загрузилось». Именно бесшумность превратила сбой в «задачи пропали».
- **UI типов.** Тип задачи в карточке/форме стал выпадающим списком с
  иконками (четыре значения в 268px сегментами не помещаются — «Исследование»
  шире целого сегмента); приоритет остался сегментами, теперь четырьмя
  (компактнее по шрифту/отступам). Проверено на 1280 и 390px — без переносов
  и горизонтального скролла.
- **Локальные копии наборов значений убраны** (`prepareTaskCard`, опции
  формы) — они ссылаются на общие типы, иначе расхождение повторится.
- **Голос:** синонимы приоритета «блокер/блокирующий/наивысший» (не
  пересекаются с HIGH, чтобы фраза не давала двух кандидатов).

  генерируется на запуск, поэтому «склонировал и запустил» работает без

**Осталось открытым:** TD-021 (автоматизации деплоя нет; секретов

@NotNull, `normalizeName('')→null`), но **колонка `sprint.name` в БД осталась
NOT NULL** из исходной миграции — предположение ТП-70 «колонка уже nullable»
было неверным. Пустое имя → null → нарушение NOT NULL.
- **Фикс:** миграция `20260709-sprint-name-nullable.xml` —
  `dropNotNullConstraint` на `sprint.name`. БД приведена в соответствие с моделью
  (`@Column`, nullable) и намерением ТП-70. Java-код не менялся.
- **Диагностика:** воспроизведено на локальном backend из main против общей БД
  (curl-тесты с корректным UTF-8 через node): rename→200, **clear name→400**,
  no-dates→200. После применения миграции (рестарт, Liquibase: «Null constraint
  dropped from sprint.name») clear name→200 (name=null). Урок: локальный backend
  на :8080 из другой сессии был на СТАРОМ коде (хранил пустое имя как ""), поэтому
  бага там не воспроизводилась — проверять на актуальном main (branch/merge integrity).
- Тесты: полный backend `./gradlew test` зелёный (юнит-тесты мокируют репозиторий,
  ограничение БД проверяется интеграционно на реальной БД — сделано вручную).
