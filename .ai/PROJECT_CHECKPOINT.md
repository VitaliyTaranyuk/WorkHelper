## Завершено 2026-08-05: фаза 5.2 открыта (ADR-027) и сделан T-510 — привязка репозитория

Владелец распорядился реализовать фазу 5.2 целиком. Первым делом это потребовало снять
собственный блокер проекта, а не обойти его молча.

**ADR-022 отменён новым ADR-027, а не проигнорирован.** ADR-022 останавливал T-510…T-519 до
базовой линии MVP-0: ценность фазы не измерена, а строить таблицы под недоказанную ценность —
тот же класс ошибки, что правила про несуществующие механизмы (T-106). Указание владельца —
достаточное основание начать, но молчаливая отмена сделала бы реестр ADR лживым (**K-40**):
следующий исполнитель прочитал бы ADR-022 как действующий запрет.

ADR-027 принимает риск **осознанно и с компенсацией**: цена ошибки удерживается на нуле
условиями, которые становятся обязательными — только аддитивные миграции с явным
`<rollback>`; существующий проект обязан работать **без единой записи** в новых таблицах
(I-03, проверяется тестом, а не намерением); каждая задача фазы — отдельный PR и отдельная
выкатка. Тогда «откат фазы» = перестать пользоваться, как и спроектировано в
`PHASE5_INVARIANTS §5`. Ценность по-прежнему не измерена — это записано честно, а не выдано
за доказанное.

**T-510 — привязка проекта к репозиторию.** Отдельная таблица `repo_binding`, а не колонки в
`project` (ADR-020): WorkHelper сам монорепо, и проект может быть связан с несколькими
репозиториями. Миграция аддитивна, идемпотентна по `preConditions` и имеет **явный
`<rollback>`** — правило №2 фазы, потому что цепочка отката иначе упирается в старые
необратимые changeSet (T-502).

**Права разведены как в остальных проектных запросах:** читать привязки может любой участник
(иначе он не увидел бы, с каким репозиторием работает его проект), менять — только владелец.
Проверка членства — тем же `CheckerUtil`, что и везде. Привязка ищется **в пределах проекта**:
id из чужого проекта даёт «не найдено», а не молча редактирует чужую запись.

**Появился раздел «Настройки проекта»** (`/project/$projectId/settings`) со ссылкой в
сайдбаре — без неё функциональность была бы недоступна пользователю (**K-32**). Это не крюк
ради одной секции: фазе он понадобится ещё трижды — правила проекта (T-511), процесс задачи
(T-515), режим доски (T-519). Глобальный `/settings` остаётся настройками пользователя: другой
скоуп.

**Пустое состояние объясняет, а не молчит** (**W-06**): «Репозиторий не привязан. Это
нормально…» — привязка необязательна по I-03, и раздел без записей это норма, а не сбой.

**Проверка:** backend **241/241** (+7: создание владельцем, отказ по дублю адреса понятным
сообщением, отказ до любой записи на чужом проекте, id чужого проекта не редактируется,
смена ветки не спотыкается о собственный адрес, чтение доступно участнику без прав владельца,
проект без привязок отдаёт пустой список), frontend **581/581** (+5), lint 0, production build
ok, SpotBugs 0 находок на новом коде — свежий гейт T-104 сразу проверил новую подсистему.

## Завершено 2026-08-03: T-104 — статический анализ backend стал настоящим гейтом

Шаг 3 quality gate («статический анализ») больше двух недель стоял с пометкой «в проекте
отсутствует». Теперь он есть и валит сборку.

**Выбран SpotBugs, а не Checkstyle — по истории отказов проекта.** Checkstyle ищет
оформление; SpotBugs ищет **дефекты**: разыменование null, проглоченные исключения,
сравнение по ссылке вместо значения. Это ровно те классы, на которых проект уже горел:
BUG-026 (NPE в `setAssignee`), BUG-034 (статусы сравнивались по ссылке, и все задачи
считались незавершёнными).

**A1 сделан замером, а не оценкой.** Первый прогон — с `ignoreFailures = true`, чтобы
увидеть объём: **244 находки**. Разбор по рангу решил всё:

| Находки | Ранг | Что это |
|---|---|---|
| 237 | 18 (низший) | `EI_EXPOSE_REP`/`EI_EXPOSE_REP2` — «геттер отдаёт ссылку на изменяемый объект» |
| 7 | 13–16 | всё остальное |

То есть 97% шума — от одного семейства детекторов, и на JPA-сущностях с Lombok это не дефект,
а устройство: Hibernate меняет сущности через сеттеры, защитное копирование сломало бы
персистентность. Исключено с письменной причиной.

**Оставшиеся 9 находок разобраны поштучно, и анализатор оправдался на первом же прогоне.**

| Находка | Вердикт |
|---|---|
| `NP_NULL_ON_SOME_PATH` в `sanitizeFileName:148` | **настоящий баг на пользовательском вводе**: `Paths.get(original).getFileName()` возвращает `null` для имени вроде `/` или `C:\`, дальше `.toString()` → NPE → 500 при загрузке файла. Исправлено |
| `NP_NULL_ON_SOME_PATH` в `upload:80` | `target.getParent()` практически не null, но полагаться молча нельзя — добавлен явный отказ вместо NPE (**K-34**) |
| 2 × `DE_MIGHT_IGNORE` в `AwaitUtils` | класс **мёртв** — не вызывается нигде во всём `backend/src`. Удалён (второй мёртвый утиль за сессию после `ValidateTask`/TD-036) |
| `RCN_REDUNDANT_NULLCHECK` в `GlobalExceptionHandler:53` | ветка `ex.getMessage()` недостижима: `getMostSpecificCause()` у Spring не бывает null. Мёртвая проверка убрана |
| 2 × `DMI_RANDOM_USED_ONLY_ONCE` в `JwtUtils` | **ложное по сути**: детектор про предсказуемый `Random`, а здесь `SecureRandom`, который засевается из системной энтропии при каждом создании. Исключено — трогать генерацию секретов ради нити производительности плохой размен (TD-019 куплен дорого) |
| `SE_BAD_FIELD` в `CustomUserDetails` | аутентификация stateless (JWT), объект никогда не сериализуется; `transient` дал бы `null` там, где сейчас гарантированно есть значение. Исключено |
| `URF_UNREAD_FIELD` в `ProjectHistoryDto` | поля DTO читает Jackson при сериализации — SpotBugs этого не моделирует. Удаление поля было бы изменением контракта API ради тишины анализатора (**W-01**). Исключено для пакета `dto` |

**Принцип исключений записан прямо в фильтре:** чинится всё, что чинится дёшево и безопасно;
исключается только то, где починка хуже находки, и **каждое исключение с причиной**.
«Заглушить, чтобы позеленело» запрещено тем же принципом, что и правила, описывающие
несуществующие механизмы (**K-40**).

**Проверка — гейт умеет падать.** Мало было получить 0 находок: временно добавлен класс с
заведомым `NP_ALWAYS_NULL`, прогон дал `BUILD FAILED` на задаче `spotbugsMain`, пробник
удалён. Без этой проверки «зелёный анализатор» неотличим от выключенного.

**Правки workflow не потребовалось:** `spotbugsMain` входит в `check`, а `check` — в `build`,
то есть существующий шаг CI `./gradlew build -x test` его уже запускает (проверено списком
выполненных задач Gradle). `spotbugsTest` отключён — у тестового кода другие нормы, и шум
оттуда обесценил бы гейт.

**Проверка:** SpotBugs 0 находок при `ignoreFailures = false`; backend **234/234, 0 падений,
0 ошибок** — посчитано по JUnit-отчётам (27 файлов), а не по строке «BUILD SUCCESSFUL».
Тесты прогнаны в ASCII-копии: из рабочей копии они не идут, кириллица в пути ломает classpath
форкнутой JVM. **CI прогнал гейт независимо** на чистом раннере — `backend-ci.yml` выполняет
`./gradlew build -x test`, то есть вместе со SpotBugs.

**Выложено на прод** (PR #254, [прогон #30843393355](https://github.com/VitaliyTaranyuk/WorkHelper/actions/runs/30843393355),
`target=backend`): контейнер прошёл `starting → healthy`, гейт сверил версию образа с
коммитом на сервере. Проверено с публичного адреса: `/health` отдаёт
`{"status":"UP","database":"UP","version":"3a803ee2341bd9ab…"}` — **ровно коммит этого
мержа**, то есть на проде работает образ именно из этого кода (механизм T-305).

**Что осталось недоказанным:** исправление `sanitizeFileName` на живом окружении не
воспроизводилось — чтобы увидеть прежний NPE, нужно загрузить файл с именем вроде `/`, а это
требует входа в приложение (**K-33**). Дефект доказан статически и логикой `Paths.getFileName()`;
регрессия исключена тем, что все 234 теста зелёные и поведение на обычных именах не менялось.

## 2026-08-03: G-10 снят разбором — аудит T-500 закрыт полностью

Последний «открытый» разрыв мультипроектности оказался недостижимым состоянием, а не
дефектом. Закрыт анализом, без единой строки кода.

**Что утверждал аудит:** «`ARCHIVED` остаётся в списке проектов, отличить его в переключателе
нельзя» — и выносил это первым вопросом владельцу (`MULTIPROJECT_AUDIT §7`).

**A1 нашёл, что вопрос поставлен не туда.** Проверены оба конца:

| Проверено | Факт |
|---|---|
| Фильтр списка | `ProjectsService:62` отсекает только `DELETED` — `ARCHIVED` действительно прошёл бы |
| Что вообще приезжает на фронт | `ShortProjectDataDto` содержит **только `id` и `name`** — статуса в ответе нет, переключатель не смог бы пометить архивный проект при всём желании |
| Можно ли заархивировать проект | **нет**: `PUT /projects/{id}/archive` есть, `archiveProject` заведён в клиенте (`projectsApi.ts:114`), но **ни одного вызова** во фронтенде |

То есть состояние «архивный проект висит в переключателе» **штатным путём недостижимо** —
заархивировать проект нечем. Вопрос владельцу переформулирован: не «показывать ли архивные»,
а «нужна ли архивация проектов вообще». Записано как **TD-037**; если понадобится — первым
шагом аддитивно добавить `status` в DTO, иначе UI будет нечем помечать.

**Побочно найдена мина — TD-036.** `ValidateTask` помечен `@Component`, метод
`validateTask()` публичен, и **никто его не вызывает** во всём `backend/src`. Внутри —
правило «задача со спринтом допустима только в `ACTIVE`-проекте», а новый проект создаётся
как **`DRAFT`** (`Project.java:64`). Код выглядит действующим правилом, но не работает; тот,
кто «починит» подключение при рефакторинге, сломает создание задач в каждом новом проекте.
Удаление не сделано попутно осознанно: это backend, а его тесты не идут из рабочей копии
(кириллица в пути) — нужен прогон в ASCII-копии, то есть отдельная работа.

**Итог по аудиту T-500: закрыты все десять разрывов.** G-1…G-3, G-8, G-9 — T-518; G-7 —
TD-028; G-4 и G-6 — сегодня кодом; G-5 — решением владельца; G-10 — этим разбором.

## Завершено 2026-08-03: TD-035 — чекпоинт перестал притворяться источником состояния

Долг был записан как «правило гигиены не может сработать». A1 нашёл дефект крупнее, и он
оказался не про размер файла.

**Исходная находка подтверждена.** `CLAUDE.md` предписывал при превышении ~200 КБ выносить
журнал **старше полугода**. Файл порог перешёл, но самой старой записи было шесть недель —
критерий отбирал **ноль** записей. Правило существовало и не могло сработать ни разу.

**A1 нашёл, что в файле две разные структуры.** Строки 1–2724 — журнал «новое сверху». А
строки 2807–2883 — блок **состояния** из фазы 0, переживший смену формата:

| Что утверждал блок | Как на самом деле |
|---|---|
| «Фаза: 0 — ЗАВЕРШЕНА, следующая — 1» | закрыты фазы 1.5, 2, 3, 4, 5.1 |
| «Активная задача: T-101 (Docker недоступен)» | T-101 не в работе; `docker-compose up -d` — штатная команда из `CLAUDE.md` |
| «Последняя завершённая: T-100» | **противоречит строке 2745 того же файла** — «Последняя завершённая: Фаза 1.5» |
| «Технический долг: TD-001…TD-004» | в реестре TD-001…TD-035 |
| «Backend tests: 37/37» | 234 |
| «DB connection: `91.211.249.37:32505`» | адрес чужого хоста из истории TD-024 |

Это ровно то, что `RULES_DELIVERY_AUDIT` назвал корневой проблемой: **три файла, описывающие
одно состояние в трёх формах**. И это K-40 в чистом виде — документ утверждал о сегодняшнем
дне то, что было верно в июне.

**A2 уточнил, что удалять.** Соблазн «снести хвост целиком» неверен: часть его (сводки фазы
0, фазы 1.5, фазы 2, Frontend Quality Audit) — это **журнал**, то есть история «почему», её
терять нельзя. Удалению подлежали только блоки, **претендующие на описание текущего
состояния**. Журнальная часть перенесена в архив как есть.

**A2 отверг и «построить механизм архивации».** Автоматизировать нечего: это ручная и редкая
операция, а ритуал на каждой итерации в этом проекте уже отказывал (TD-027). Исправлен
**критерий**, а не добавлен механизм: отбор по объёму вместо возраста — тогда правило
исполнимо на проекте любого возраста.

**Сделано.** Журнал 2026-06-21…2026-07-06 (55 записей, 1044 строки) вынесен в
`.ai/checkpoint-archive/2026-06-21--07-06.md`; блок состояния удалён; в основном файле
осталась ссылка на архив. Было 2883 строки и 231 КБ, стало **1772 строки и 178 КБ** — ниже
порога. В `CLAUDE.md` закреплён запрет держать состояние в чекпоинте и уточнено, что искать
старые решения нужно `grep`-ом по всему `.ai/`, включая архив.

**Проверка:** разрез сошёлся арифметически — 1762 оставленных + 1044 перенесённых + 77
удалённых = 2883 строки исходника; заголовков 33 + 55 = 88, как было. Содержимое записей не
менялось: перенос сделан диапазоном строк, а не пересказом.

**Урок в копилку — третий раз за сессию соврал инструмент, а не механизм.** Правку
разделителя я выполнял через `python3` в Git Bash; команда напечатала «Python» и **ничего не
сделала** — это заглушка Windows Store, а не интерпретатор. Хвост файла в выводе при этом
выглядел исправленным, потому что показывал строки уже после проблемного места. Поймано
повторным независимым измерением (`sed -n`), а не доверием к отчёту команды.

## Завершено 2026-08-03: T-308 — пустой список колонок больше не роняет экран

Первая задача, исполненная по новому протоколу целиком, включая A0.

**A0 (актуальность).** Описание подтверждено дословно: `useProjectData.ts:105` —
`reduce` без начального значения, и фолбэк на `mapped.statuses` при пустом списке тоже
пуст. Вердикт — работать, описание не переписывать.

**A1 нашёл, что предпосылка записана неверно.** TD-031 объяснял недостижимость тем, что
«колонки заводятся вместе с проектом». Само по себе это ничего не гарантирует: удаление
колонки в проекте **есть** (`TaskStatusController:62`). Инвариант держит другое —
`TaskStatusService.deleteStatus:182-185` отвергает удаление `defaultTaskStatus` и
`isSystemStatus`, поэтому шесть системных колонок неудалимы. Запись долга поправлена.

**A2 нашёл, что «недостижимо» верно только для БД.** `mapProjectDtoToProjectInfo:10`
превращает **отсутствующее** поле `statuses` в `[]` — значит пустой список приезжает и без
аномалии данных, достаточно расхождения контракта. Это класс **W-08**: фронтенд обязан
деградировать, а не бросать. Дефект перестаёт быть «только для фикстуры».

**Вопрос задачи («молчать или показывать сообщение», W-06) оказался ложной дихотомией.**
Верный ответ — третий: `resolveStatus` становится `undefined`. Подставленный статус был бы
именно молчаливым отказом — он позволил бы «завершить» задачу в несуществующую колонку.
Сообщение при этом не место хука: хук не рисует UI, а доска уже деградирует сама
(`Board.tsx:126` — `activeProject?.statuses ?? []`).

**Радиус изменения проверен, а не предположен.** `resolveStatus` читают два места:
`TaskCardContent.tsx:150` уже работал с ним как с необязательным (`completedStatus?.id`,
`Boolean(completedStatus)`), `FinishSprintModal.tsx:44` — нет, там добавлен `?.`. Поведение
на нормальных данных не изменилось: при отсутствующем проекте оптическая цепочка и раньше
давала `undefined`. Сплошной проход по `.reduce(` во фронтенде: три вызова, два уже с
начальным значением (`Board.tsx:203`, `FinishSprintForm.tsx:127`) — незакрытым был ровно один.

**Проверка (V):** frontend **559/559** (+3), lint 0, production build ok (`vite build &&
tsc -b`, exit 0 — тайпчекер подтвердил, что других небезопасных потребителей нет).
Тест проверен на способность падать: с откаченным фиксом 2 из 3 падают с
`TypeError: Reduce of empty array with no initial value`, третий (негативный контроль на
нормальных данных) проходит в обоих случаях.

**Не сделано осознанно:** отдельного сообщения «у проекта нет колонок» на доске не
добавлено. Состояние недостижимо штатным путём, доска и так рисует пустой набор колонок, а
UI под гипотетическое состояние — спекуляция (**K-23**).

**Выложено на прод** (PR #242, [прогон #30798184443](https://github.com/VitaliyTaranyuk/WorkHelper/actions/runs/30798184443),
`target=frontend` — backend не менялся): гейты прогона прошли (ассеты отдаются с верным
content-type, `/health` = UP, выложен бандл именно этой сборки). Проверено с публичного
адреса: `/health` → `{"status":"UP","database":"UP","version":"8b19ed3abb32…"}` (версия
образа backend прежняя — он не пересобирался, это ожидаемо), бандл сменился на
`index-CNuCivzV.js`, `index.html` по-прежнему `no-cache`. Приложение открывается, React

## Завершено 2026-07-30: T-305 — деплой доказывает, что запущен образ из нового кода

Гейт умел проверять, что на сервере нужный коммит и что приложение отвечает, но не что
работает образ **из этого кода**. `build.gradle` считает версию через `git rev-parse`, а в
docker-контекст `.git` не копируется — внутри образа версия вырождалась в `0.0.1-`. Это тот
же класс отказа, из-за которого ТП-208 три недели считалась развёрнутой (TD-023): для
фронтенда он закрыт сверкой бандла, для backend оставался открытым (TD-030).

Теперь SHA приезжает build-аргументом, `/health` отдаёт поле `version`, а шаг деплоя падает,
если оно не совпадает с коммитом на сервере.

**Две поправки, которые дал A2 к первоначальному плану:**

- `ARG` объявлен **только в рантайм-стадии** Dockerfile, после `COPY --from=build`. В стадии
  сборки он инвалидировал бы кэш слоёв, и каждый деплой пересобирал бы зависимости Gradle
  на VDS с одним CPU.
- Сверять надо с коммитом **на сервере**, а не с `github.sha`: проверка `merge-base
  --is-ancestor` намеренно допускает, что сервер ушёл вперёд, и строгое равенство давало бы
  ложные падения на ровном месте.

Отсутствие аргумента не ломает сборку — версия становится `unknown`, и гейт об этом честно
падает вместо молчания (**W-06**).

**Проверка:** backend 234/234, production build ok. Выложено и проверено на проде ([прогон #30568436225](https://github.com/VitaliyTaranyuk/WorkHelper/actions/runs/30568436225)): гейт сверил `версия в образе` и `коммит на сервере` — оба `8b19ed3abb32…`; `/health` на публичном адресе отдаёт тот же SHA, совпадающий с `main`.

## Завершено 2026-07-30: три «грабли окружения» — две починены, одна оказалась миной

Разбор накопившихся обходных путей: каждый прошёл A1 → A2, и один из трёх фиксов
контр-анализ отменил.

**1. Кэш статики (починено, дошло до прода).** Измерено, а не предположено: `/` и
`/assets/*` отдавались **без единого заголовка кэширования** — только `ETag`/`Last-Modified`.
Браузер кэшировал `index.html` по эвристике, и после деплоя пользователь продолжал грузить
прежний бандл до жёсткой перезагрузки; файлы с хешем в имени, наоборот, перезапрашивались
каждый раз. Теперь `index.html` — `no-cache` (ревалидация, ETag отдаёт 304), `/assets/` —
`public, max-age=31536000, immutable`. Проверено с публичного адреса: `/`, `/main`,
`/index.html` → `no-cache`; бандл → `immutable`.

**Отдельная история — пять «отказов» подряд, которые оказались ошибкой измерения.**
Post-check упорно показывал, что заголовок появляется везде, кроме голого `/`, и каждый раз
честно откатывал конфиг. Я последовательно менял механизм — `location = /index.html`,
`add_header` внутри `location /`, на уровне server, `location = /` с `try_files`,
`rewrite` — и каждый раз получал тот же результат, выстраивая всё более сложное объяснение
про внутренний редирект index-модуля. **Все эти объяснения были неверны.** Настоящая
причина: `/` пробуется **первым**, через доли секунды после `nginx -s reload`, а остальные
пути — секундой позже. Воркеры после reload подменяются асинхронно, и первый запрос
обслуживал ещё старый воркер со старым конфигом. Картина сходится идеально: что пробовалось
первым — заголовка не имело, что следом — имело. Скрипт теперь ждёт, пока новый конфиг
начнёт отвечать, и только потом проверяет.

Урок в копилку проекта: **сначала подозревай измерение, а не механизм** — особенно когда
одинаковый симптом переживает пять разных фиксов. И: проверка сразу после `reload` меряет
прошлое.

**A2 нашёл, что правки конфига было бы недостаточно:** `infra/nginx-vds.conf` **не является
работающим конфигом прода** — там нет даже 443-блока, который добавил certbot, и ни один
пайплайн этот файл на сервер не применяет. Поэтому вместе с конфигом добавлен
`infra/apply-nginx-cache.sh` по контракту уже существующего `apply-nginx-ws.sh`
(идемпотентность по маркеру, бэкап → вставка → `nginx -t` → reload → post-check →
автооткат) и шаг в `deploy.yml`, который его вызывает. Post-check проверяет заголовки через
публичный адрес: не появились — конфиг откатывается. Вставка прогнана локально на макете
конфига с 443- и 80-блоками.

**2. Порядок сборки (починено).** `npm run build` был `tsc -b && vite build`, а дерево
маршрутов TanStack генерирует Vite-плагин — то есть **после** проверки типов. Новый маршрут
(T-518) ронял сборку, пока не сделаешь `npx vite build` вручную. Порядок переставлен:
`vite build && tsc -b`. Гейт не ослаблен — проверено негативным прогоном: файл с ошибкой
типов даёт `exit=2`, CI останется красным.

**3. Хуки lefthook (НЕ трогал — фикс из реестра оказался ошибочным).** TD-027 предлагал
однострочник `"prepare": "lefthook install"`. A2 показал, что он **сломал бы каждый
коммит**: конфиг `frontend/lefthook.yml` запускает `npm run lint` с рабочим каталогом =
корень репозитория, где нет `package.json`; lefthook, запущенный из корня, конфига во
`frontend/` не найдёт; хуки живут в **общем** `.git/hooks` и зашивают абсолютный путь того
worktree, из которого ставились (установленный сейчас `prepare-commit-msg` указывает на
временный worktree и уже сломан — отсюда «Can't find lefthook in PATH» на каждом коммите);
фильтров по файлам нет, поэтому линт и сборка запускались бы даже на коммитах в `.ai/*.md`.
Запись TD-027 переписана под факты с настоящим планом фикса.

**Побочно — TD-033 (K-40):** `infra/NGINX_WS_RUNBOOK.md` утверждает, что WS-локация
применяется шагом пайплайна `deploy-main.mjs`. Ни файла, ни шага в репозитории нет — то есть
документ описывает несуществующий механизм, а локация на проде держится ручным запуском.

**Живая проверка нашла дефект, который не поймали ни тесты, ни одиночный проект** —
и он мой, из этой же задачи: точка входа `/main` уводила **то в нужный проект, то в первый
по алфавиту** при одном и том же состоянии сервера. Причина — гонка: список проектов
(`/projects/for-user`) и ответ о последнем открытом (`/projects/last`) — два разных
запроса, и в `useActiveProjectId` запасной вариант `userProjects[0]` подставлялся, не
дожидаясь второго. На одном проекте дефект невидим: первый проект и последний — один и тот
же. Фикс: запасной вариант разрешён только после ответа сервера (`isFetched`). Закреплён
постоянным репродьюсером — без гарда тест падает (проверено откатом строки).

бандл `index-C00xClbS.js`): при `last = B` три загрузки `/main` подряд открыли B. Окно
гонки измерено на тех же прогонах — порядок ответов действительно плавает: `for-user`
763 мс против `last` 805 мс в одном прогоне и 804 против 689 в другом. В первом случае
список опередил ответ о последнем проекте, то есть прежний код увёл бы в WorkTask, —
новый открыл нужный проект.

Состояние прода восстановлено: рабочим проектом снова WorkTask, тестовые вкладки закрыты.

## Завершено 2026-07-29: T-518 — проект переехал из серверного поля в адрес страницы

Корневой разрыв мультипроектности (T-500): «текущий проект» был не параметром URL, а полем
`user.last_project_id`, которое переписывал **обычный** `GET /projects/{id}`. Чтение меняло
глобальное состояние — отсюда G-1…G-3: доску нельзя передать ссылкой, две вкладки с разными
проектами невозможны, а взгляд в бэклог другого проекта уводил за собой доску.

**A1 нашёл то, чего не было в аудите** (аудит смотрел на выбор проекта, а не на данные доски):

| Найдено | Почему важно |
|---|---|
| `TaskService.getProjectTaskByUserGuid()` — эндпоинт **доски** `GET /tasks/tasks-in-project` вообще не принимал проект и брал его из `last_project_id` | Одного маршрута было бы мало: доска продолжила бы показывать «последний» проект независимо от адреса |
| `getProjectDataByFilter` (`POST /{id}/filtered`) писал `last_project_id` тем же способом | Второй побочный эффект того же класса; потребителей у эндпоинта нет |
| Роутер-хук в `useProjectData` недопустим | Его вызывают компоненты NiceModal-модалок вне Router-контекста — это прод-инцидент «белый экран» ТП-172 (**R-02**) |

**Решение — ADR-026.** Проект живёт в URL: доска получила `/project/$projectId/board` рядом
с уже существующими `backlog`/`sprint`/`calendar`. `last_project_id` остался, но меняется
**только** явным `PUT /projects/{id}/last` и отвечает на единственный вопрос — где открыть
`/main` и следующий вход. Шов на фронтенде — стор вкладки `currentProjectStore`, куда
маршруты кладут `projectId`: router-хук в общем `useProjectData` уронил бы модалки (R-02).

`/main` сохранён как точка входа и редирект: на него ведут **14 мест** приложения (логин,
приглашение, встреча, голосовые команды, кнопка «назад»), переписывать их ради нового
адреса значило бы тронуть половину приложения (**K-23**). Пользователь без проектов теперь
видит объяснение вместо пустого экрана (**W-06**).

**Что закрыто:** G-1 (выбор проекта), G-2 (мутирующий GET), G-3 (доска без deep-link),
G-8 (удалённый проект больше не «залипает»: точка входа проверяет доступность и берёт
первый доступный), G-9 (карточка задачи закрывается при переключении).
**Отложено сознательно:** G-4 (`/task/$code` резолвится в текущем проекте) — он связан с
G-5 (уникальность `project.code`) и требует миграции, делать их нужно вместе.

**Побочно:**
- эндпоинт доски получил **явную проверку членства**: раньше проект приходил из доверенного
  серверного поля, теперь — из URL, и доверять ему нельзя (тест на чужой проект добавлен);
- `useChangeProject` удалён как мёртвый: инвалидации кэшей ему больше не нужны — ключи
  запросов содержат `projectId`, у нового проекта они просто другие (**K-32**);
- зависимость T-518 от T-510 в реестре снята: привязка репозитория к навигации отношения
  не имеет, а ADR-022 разрешает T-518 до MVP-0;
- **TD-031** (новый): `useProjectData` вычисляет завершающий статус через `reduce` без
  начального значения — проект без колонок уронил бы экран. Штатным путём недостижимо
  (колонки заводятся вместе с проектом), вскрылось на тестовой фикстуре.

**Проверка:** backend 234/234 (+7), frontend 553/553 (+3: адрес важнее серверного
«последнего», без адреса работает прежняя точка входа, доска запрашивает задачи по проекту
из адреса), lint 0, production build ok.

**Выложено на прод** (PR #222, [прогон #30490671978](https://github.com/VitaliyTaranyuk/WorkHelper/actions/runs/30490671978)):
контейнер `starting → healthy`, `/health` → `UP`, бандл `index-CoMXksyL.js`. Косвенно
подтверждено, что выложен именно новый фронтенд: в бандле есть маршрут
`project/$projectId/board` и **больше нет** обращения к `tasks-in-project`.

**Функциональная проверка на проде (W-03) ждёт входа владельца** — вкладка браузера
окружения пересоздалась и разлогинилась, пароли агент не вводит (K-33). Проверить нужно:

## Завершено 2026-07-29: TD-028 — picker перестал раздавать всю базу пользователей

`GET /users/picker` брал `userRepository.getUsers()` — **всех пользователей системы**, и
`UserPickerDto` отдавал их `email`. Любой участник любого проекта получал имена и почту
всех, кто зарегистрирован (K-36), и мог упомянуть человека, которому проект недоступен.

**Контр-анализ отверг очевидный фикс.** «Добавить `projectId` и отфильтровать по проекту»
сломало бы приглашение в проект: тот же эндпоинт использует `InviteUsersModal`, а
приглашать нужно ровно тех, кого в проекте **ещё нет**. Один эндпоинт обслуживал два
взаимоисключающих требования — поэтому пути разделены:

| Сценарий | Как теперь |
|---|---|
| @mention в комментариях | `GET /users/picker?projectId=…` — **участники проекта**, членство вызывающего проверяет `CheckerUtil` (как во всех остальных запросах) |
| Приглашение в проект | `GET /users/lookup?projectId=&q=` — **точное** совпадение по username или email, уже добавленные исключаются, **email в ответе не возвращается** (его и так ввели) |

**Почему точное совпадение, а не «поиск как раньше, но под ролью».** Ролью каталог не
закрыть: владельцем проекта становится любой, кто создал проект (`POST /projects/create` —
PROJECT_MEMBER+), то есть подстроковый поиск по всей базе остался бы перечисляемым для
кого угодно. Точное совпадение сохраняет рабочий сценарий «пригласить известного человека»
(так устроено в Slack, Notion, Jira), а кого не знаешь по имени — приглашается ссылкой
(ТП-35, путь не тронут).

получателя через `findByUsername` по всей базе: `@username` постороннего создавал ему
уведомление с кодом чужой задачи и ссылкой, которая у него не открывается. Picker таких
больше не предлагает, но руками `@` пишут — поэтому проверка членства добавлена и в
уведомления.

**Что осталось как было (и почему):** assignee-picker в карточке задачи брал участников из
данных проекта (`activeProject.users`), а не из этого эндпоинта, — «мёртвого выбора
исполнителя», упомянутого в описании долга, в UI не было; трогать нечего (K-23).

**Проверка:** backend 227/227 (+7: picker отдаёт участников и не читает всю базу, чужой
проект → отказ, lookup находит по точному совпадению / игнорирует подстроку / пропускает
уже добавленных / не ходит за одним символом, упоминание постороннего не создаёт

## Завершено 2026-07-29: TD-029 — гейт деплоя перестал выдавать сломанный релиз за успешный

Задача звучала как «добавить `-f` в healthcheck». Контр-анализ показал, что **одного `-f`
было бы недостаточно**: в том же гейте лежал второй дефект, который обесценивал первый.

**Что было измерено, а не предположено:**

| Проверка | Что делает на самом деле |
|---|---|
| `curl -s …/auth/login` (healthcheck) | GET на POST-эндпоинт → **405**, но `curl` без `-f` завершается с кодом **0** (проверено на проде: `exit=0`; с `-f` — `exit=22`). Контейнер становился `healthy`, отвечая ошибкой на всё |
| `case "$status" in *healthy*)` (шаг ожидания в `deploy.yml`) | Строка `Up 2 minutes (unhealthy)` **содержит** подстроку `healthy` — проверено: совпадает. Гейт принимал нездоровый контейнер за здоровый, поэтому `-f` сам по себе ничего бы не изменил |
| `curl / → 200` (smoke фронта) | nginx на VDS настроен `try_files $uri $uri/ /index.html`: **несуществующий** `/assets/index-NETAKOGO.js` отдаётся с кодом **200** и типом `text/html` (проверено на проде). Проверять ассеты по коду ответа бессмысленно — годится только content-type |

**Что сделано.**

- `GET /work-task/api/v1/health` (`HealthController` + `HealthService`, permitAll) — реальный
  GET-эндпоинт, который **ходит в пул соединений** (`Connection#isValid`), а не просто
  подтверждает, что порт слушают. Недоступная база → **503**, а не 200 с телом «DOWN»:
  гейт видит код, а не тело. Наружу отдаётся только `{"status","database"}` — причина в
  логах (K-34).
- Healthcheck переведён на `curl -sf … || exit 1` — ровно та форма, что уже используется у
  glitchtip в том же файле (K-38).
- Шаг ожидания читает статус точным значением (`docker inspect --format
  '{{.State.Health.Status}}'`), а не поиском подстроки.
- Перед сборкой на сервере проверяется, что выкатываемый коммит **есть в HEAD** сервера
  (`git merge-base --is-ancestor`): собирать не тот код и потом убеждаться, что «контейнер
  поднялся», бессмысленно. Шаг разделён на «обновить код» и «пересобрать» — по имени
  упавшего шага теперь видно, что именно сломалось.
- Smoke фронта проверяет: `/` отдаёт index.html приложения → он ссылается на ассеты →
  **каждый ассет реально отдаётся с типом JS/CSS**, а не подменён SPA-фолбэком → публичный
  `/health` отвечает `UP` (сквозной путь nginx → backend → база). Отдельным шагом —
  сверка выложенного бандла с собранным в этом же прогоне: молчаливое «задеплоили, но не
  то» (TD-023) для фронтенда закрыто.
- `DeployGateContractTest` держит связь «конфигурация деплоя ↔ код»: путь в healthcheck
  совпадает с `HealthController.PATH`, `curl` вызывается с `-f`, гейт не сравнивает статус
  по подстроке. `backend-ci.yml` теперь запускается и на правку `docker-compose.vds.yml` /
  `deploy.yml` — иначе этот тест на них бы не прогонялся.

**Найдено побочно и зафиксировано (TD-030):** доказать, что на сервере работает образ
**из нового кода**, деплой по-прежнему не может — у backend нет отпечатка версии.
`build.gradle` считает версию из `git rev-parse`, но в docker-контекст `.git` не попадает,
и внутри образа версия вырождается в `0.0.1-`. Для фронтенда этот класс закрыт сверкой
бандла, для backend — нет.

**Проверка:** backend 220/220 (+9: работоспособность БД и возврат соединения в пул, коды
200/503, три контракта гейта), production build ok. Логика smoke-шага прогнана против прода
как есть — на живых ассетах проходит, на заведомо отсутствующем падает.

**Проверено на проде** (PR #216, [прогон #30435932759](https://github.com/VitaliyTaranyuk/WorkHelper/actions/runs/30435932759)):

| Гейт | Что показал деплой |
|---|---|
| Коммит на сервере | `a98eb9d…` — совпал с выкатываемым, сборка пошла от него |
| Ожидание готовности | `healthcheck: starting` → `starting` → `healthy`; статус читается точным значением |
| Ассеты | `/assets/index-DMZcIld-.js (application/javascript)`, `…css (text/css)` |

| Свежесть бандла | выложенный бандл совпал с собранным в прогоне |

Проверено отдельно на живом адресе: `GET /work-task/api/v1/health` без авторизации →

нельзя: описание хранится и редактируется как простой текст, ломать это ради индикации —
несоразмерно. Поэтому расшифровка живёт в **панели прямо под полем** (`DictationLivePanel`),
где распознанное окончательно идёт обычным текстом, а уточняемое — курсивом и приглушённо.
В поле текст попадает один раз — когда человек закончил сессию; это и есть требуемый сигнал
«аудионабор завершён, текст обычный».

**Диктовка стала сессией.** Заканчивает её только человек: **Enter** — вставить,
**Esc** — отменить, кнопка микрофона — то же, что Enter. Паузы больше не обрывают запись
(`keepAlive` в `useSpeechRecognition` — тот же механизм перезапуска, что был у командного
режима ТП-111, но без стоп-фразы). Обе клавиши перехватываются на фазе capture: иначе Enter
ушёл бы переводом строки в `textarea`, а Esc закрыл бы модалку вместе с несохранённой
диктовкой. Shift+Enter намеренно оставлен полю.

**«Создать» прямо во время диктовки.** Точки отправки (`CreateTaskModal`,
`CreateTaskDetails`, `TaskCardContent`) вызывают `finalizeActiveDictation()` ДО чтения
значений формы — иначе последняя фраза не доехала бы до задачи. Для этого в
`useSpeechRecognition` добавлен `finish()`: он отдаёт накопленное **синхронно** и вместе с
недоговорённым `interim`-хвостом, не дожидаясь браузерного `onend` (тот приходит через
сотни миллисекунд — обработчик отправки его бы не дождался). Реестр активной сессии —
модуль `activeDictation`, а не контекст/стор: микрофон один, значение нужно синхронно внутри
обработчика, подписки и ре-рендеры здесь ничего не дают.

**A2 нашёл две вещи, пропущенные в A1:**
1. Замена `form.handleSubmit(...)` на собственный обработчик снимала `preventDefault` —
   Enter в однострочном «Названии» отправлял бы форму нативно и **перезагружал страницу**.
   Обработчики теперь принимают событие и гасят его сами.
2. Сессия, которая не обрывается по тишине, — это забытый включённый микрофон. Добавлен
   предохранитель: 60 секунд без единого распознанного слова закрывают сессию
   (`SILENCE_LIMIT_MS`), таймер перезапускается на каждом фрагменте.

**Сначала было сужено, затем доделано в том же дне** (владелец справедливо спросил, какие
проблемы этому мешают — технических не было, это было решение по объёму, и оно оказалось
неверным):

1. **Диктовка комментария** переведена на ту же живую сессию. Довод «реплика короткая»
   не выдержал проверки: жалоба «наговариваешь в пустоту» относится к комментарию ровно
   так же. Старый `DictationButton` удалён — после перевода он остался без вызовов
   (**K-32**).
2. **Описание доводится в фоне у уже созданной задачи.** «Создать» во время диктовки
   отдаёт локально отформатированный текст, а вычищенный вариант приезжает через
   несколько секунд в закрытую форму — и раньше просто пропадал.

Разбор второго: **второго запроса к модели не делается**. `executeVoiceAction` отдаёт
наружу тот самый промис, который уже ждёт сам (`onFieldEnhancement`), конвейер остаётся
единственным местом, где живёт улучшение. Промис кладётся в одноразовый слот
(`activeDictation`, TTL 60 с), `useCreateTask` его забирает и применяет — но только если
задача создана **именно этим** текстом: успело улучшение попасть в форму до отправки или
пользователь дописал руками — слот молча отбрасывается. Сервер проверяет то же самое ещё
раз, `PUT /tasks/{projectId}/{taskId}/auto-description` с compare-and-set по
`expectedDescription` (симметрично `auto-title` из ТП-240).

Побочно найдено при переводе комментария: `submit` читал `text` из замыкания `useState`, а
диктовка дописывает его в том же обработчике — отправился бы комментарий БЕЗ последней
фразы. Значение поля продублировано в ref. Плюс кнопка «Отправить» была бы мёртвой во
время диктовки (поле ещё пустое) — теперь она активна, пока идёт запись (**F-008**).

**Тесты:** backend 211/211 (+2: дописывание описания и no-op при изменённом описании),
frontend 545/545 (+19: сессия распознавания — пауза не обрывает, `finish` отдаёт хвост,
текст не отдаётся дважды; Enter/Shift+Enter/Esc; `finalizeActiveDictation`; панель живой

## Завершено 2026-07-29: ТП-239 + ТП-240 — создание и удаление задачи перестали ждать сеть, авто-название стало качественным

Две задачи владельца оказались **одним дефектом**: улучшение названия через DeepSeek
вызывалось синхронно на клике «Создать» с интерактивным таймаутом 5 с.

**Замер на живом проде (а не рассуждение).** Через перехват XHR в браузере:

| Что | До |
|---|---|
| `POST /voice/enhance-text` (TITLE) на клике «Создать» | **5003 мс → status 0 (оборван по таймауту)** |
| `POST /tasks/create` | 2767 мс |
| Модалка создания закрылась | **через ~8 с после клика** |
| `DELETE /tasks/…` | 2481 мс |
| Карточка после удаления закрылась | **через 9054 мс** |

Отдельно замерен сам эндпоинт на тех же данных: **3.5–6.5 с** и осмысленные названия
(«Ускорить создание задачи и вынести обработку описания в фон»). То есть лимит в 5 с рубил
примерно половину ответов: пользователь платил пятью секундами ожидания **и** получал
детерминированный фолбэк — ровно те названия, на которые жалуется ТП-240 («Необходима
доработка этого механизма»).

Удаление тормозило по другой причине, найденной в коде и подтверждённой в сети: `onSuccess`
в `useDeleteTask` **возвращал** промис `invalidateQueries`, а react-query ждёт возвращённый
из `onSuccess` промис перед резолвом `mutateAsync`. Карточка висела до конца рефетча доски
(6.3 с), плюс бесполезный рефетч только что удалённой задачи (404). Остальные мутации
проекта возвращают `undefined` — расходилась ровно одна.

**Решение — «создать сразу, улучшить фоном»** (паттерн Jira/Linear для AI-обогащения):

- `buildCreateTaskPayload` стал **синхронным** и в сеть не ходит; `prepareTaskCardAsync`
  удалён как мёртвый.
- Улучшение названия перенесено в `upgradeAutoTitle` — вызывается из `useCreateTask.onSuccess`
  **без ожидания**, с фоновым бюджетом 30 с вместо интерактивных 5 с.
- Признак `autoTitle` едет вместе с DTO: правило «название пользователя неприкосновенно»
  теперь проверяется в одном месте, а не по факту пустой строки в трёх.
- `useDeleteTask` больше не возвращает промис инвалидации; попутно добавлена инвалидация
  `sprints` — без неё удалённая задача жила в списках спринтов и бэклога до поллинга.
- Кнопки «Создать» и «Удалить задачу» показывают спиннер: жалоба была буквально «нажимаю —
  ничего не происходит», а серая кнопка от этого неотличима.

**Почему новый эндпоинт, а не существующий `updateTask`.** `updateTask` заменяет карточку
целиком (`setTitle/setPriority/setDescription/setTaskType` без проверки на null — это уже
зафиксировано в `useVoiceServices`: «требует полный DTO … fetch-merge»). Фоновый вызов
откатил бы всё, что пользователь успел изменить за эти секунды. Добавлен точечный
`PUT /tasks/{projectId}/{taskId}/auto-title` в духе существующих `archive`/`restore`, с
**compare-and-set** по `expectedTitle`: успели переименовать руками — запрос становится
no-op, а не затирает правку. Изменение попадает в историю задачи как обычная смена названия.

**A2 нашёл сценарий, пропущенный в A1:** карточку можно открыть из тоста «Открыть» ЗА те
секунды, пока улучшение в пути, — и сохранение вернуло бы старое название из формы RHF
(defaultValues не обновляются). Закрыто синхронизацией поля `taskTitle` с сервером, пока
пользователь его не трогал (`isDirty`-гард, `setValue` без `shouldDirty`).

**Тесты:** backend 209/209 (+2: применение авто-названия и no-op при изменённом названии),
frontend 526/526 (+8, из них постоянные репродьюсеры: «создание не ходит в сеть» и

## Завершено 2026-07-28: задачу из бэклога стало можно завершить (ветка `feature/close-task-from-backlog`)

Найдено при закрытии собственных карточек: задачу в Бэклоге **нельзя было отметить
выполненной**. В карточке селектор статуса не отображался вовсе, а бэкенд отвергал попытку
с `BadRequestException` (ТП-74). Единственный путь — протащить задачу через активный спринт,
что **искажает историю спринта**: задача в нём не выполнялась.

**Анализ вскрыл противоречие внутри кода**, а не просто неудобство:

| Решение | Что говорит | Где |
|---|---|---|
| **ТП-49** | «спринт на статус не влияет», «оси независимы» | `TaskPlacementService:87,120` |
| **ТП-74** | статус можно менять только у задачи доскового спринта | `TaskService:206` |

Второе частично отменяло первое. Рынок при этом единодушен: в Jira, Linear, ClickUp статус
задачи **не зависит** от того, в спринте она или нет.

**Решение — разрешить вне доски ровно один переход: в завершающую колонку.** Промежуточные
колонки (`In Progress`, `Review`) вне доски по-прежнему запрещены — там намерение ТП-74
верное, у задачи вне доски нет позиции на доске. Но «завершено» — это не позиция, а **факт**,
и он осмыслен всегда. Независимость осей ТП-49 восстановлена там, где она осмысленна.

- **Backend** (`TaskService.updateTaskStatus`): запрет заменён на условный, серверная защита
  от обхода через API сохранена. Завершающая колонка берётся из `completedBoardStatus` —
  **того же источника, что и выборка «Завершённых»**, чтобы «завершил» и «попало в
  завершённые» не могли разойтись. Нет завершающей колонки → отказ, а не молчаливый пропуск.
- **Frontend** (`TaskCardContent`): вне доски селектор показывается с двумя вариантами —
  текущий статус и завершающий — и подписью «Вне активного спринта задачу можно только
  завершить». Источник завершающей колонки — существующий `activeProject.resolveStatus`
  (фронтовый аналог того же правила).

**Рассмотрено и отклонено:** выводить в UI архивацию. Механизм существует и не ограничен
спринтом (`archiveTask`, T-151), но семантика другая — «убрать в архив», а не «выполнено»;
в «Завершённых» задача получила бы лейбл «В архиве» вместо «Готово».

**Побочно вскрыто:** эндпоинты архивации (`archive`/`restore`/`bulk/archive`, задачи T-151 и
T-152 со статусом COMPLETED) **не выведены в UI ни одной кнопкой** — недоступная
функциональность по **K-32**. Отдельная задача, в этот скоуп не бралась.

**Тесты:** backend 207/207 (+2 новых: завершение вне доски разрешено; отказ, если завершающей
колонки нет; уточнён существующий тест ТП-74 — промежуточный статус вне доски по-прежнему
отвергается). Frontend 522/522 (+2 новых), lint 0, production build ok. **Проверено, что
новый тест краснеет при откате фикса.**

Backend-тесты в рабочей копии не запускаются (кириллица в пути ломает classpath форкнутой
JVM — падают все 23 класса, включая `TestFixtures`); прогон выполнен на копии в ASCII-пути.

## Завершено 2026-07-28: T-504 — ADR доставки правил (ADR-023..025). Фаза 5.1 закрыта

Результат — `.ai/ARCHITECTURE.md` §Доставка правил агенту. Кода задача не касалась.

**Главный вопрос задачи оказался неочевидным: не создаст ли `AGENTS.md` тот самый дубль,
который только что снял T-107?** Проверка показала, что создаст: из семи разделов
`CLAUDE.md` специфичен для Claude Code лишь «Старт сессии» (порядок загрузки — свойство

от файла тоже нельзя: без него весь корпус привязан к одному вендору.

**ADR-023 разрешает это условием, а не запретом.** Дубль допустим тогда и только тогда,
когда он **машинный и односторонний**: `.ai/PROJECT_RULES.md` + `CLAUDE.md` → `AGENTS.md`,
файл помечен «сгенерирован, не редактировать» и коммитится в репозиторий. Именно это
отличает его от дубля, снятого T-107: тот был **рукописным** и потому разошёлся, породив
два противоречия (T-106). Машинный односторонний дубль разойтись не может по построению, а
ручная правка `AGENTS.md` становится дефектом, а не изменением правил.

**ADR-024 сузил контракт MCP-сервера (T-517).** После ADR-017 и ADR-023 правила уже доезжают
файлами и работают без сети — отдавать их ещё и по MCP значило бы завести второй источник
того же содержания, то есть повторить исходную ошибку. MCP отвечает за то, чего в файлах нет
и быть не может: получить задачу и её контекст, вернуть статус, отправить метрики прогона.

**ADR-025 зафиксировал деградацию без платформы:** репозиторий (правила, профиль, уроки, ADR,
сгенерированный `AGENTS.md`) работает всегда, платформа нужна только для задач и телеметрии.
При недоступном WorkTask теряется постановка задач, но **не метод работы** — это и есть
проверяемый критерий T-514 «работает без подключения».

## Завершено 2026-07-28: T-503 — ADR целевой модели данных (ADR-017..022)

Результат — `.ai/ARCHITECTURE.md` §Phase 5. Кода задача не касалась: спроектированы
`repo_binding`, `rule_set`, `rule`, `process_step` с полями и связями.

**Контр-анализ нашёл противоречие в собственных планах проекта, и его пришлось разрешить
до проектирования схемы.** `PLATFORM_PRODUCT_MAP §3` помещает `Rule` в облако и тут же
требует «в репозитории — суть продукта», а T-514 требует, чтобы правила работали **без
подключения к WorkTask**. Если бы схему построили поверх этой двусмысленности, получилось бы
хранилище, чьё содержимое не переживает откат кода, не видно в PR и недоступно при
недоступной платформе.

**ADR-017 разрешает это разделением ролей:** БД — библиотека и редактор переносимых наборов,
но **источник, который читает агент, — файлы репозитория**. Экспорт (T-514) материализует
правила, и рабочей является материализованная копия.

Остальные решения выведены из существующего кода, а не изобретены:

| ADR | Решение | На чём основано |
|---|---|---|
| **018** | Уровень правила — поле (`CORE`/`PACK`/`PROFILE`), «общий» набор = `rule_set` с `project_id = null` | Прецедент nullable-связи есть (`Notification.project_id`); иерархия наборов ради трёх значений — усложнение без пользы |
| **019** | Копирование правил при создании проекта — **ещё один шаг рядом с существующими** | Механизм уже работает: `createProject` вызывает `createDefaultStatuses` (из enum `StatusName`) и `createDefaultSprint`. Новая парадигма не нужна (K-38) |
| **020** | `repo_binding` — отдельная таблица, не колонки в `project` | WorkHelper сам монорепо; таблица поддерживает N репозиториев и следует паттерну `TaskStatus`/`Sprint` |
| **021** | Процесс задачи принадлежит проекту и копируется вместе с правилами; связь задачи с этапом nullable | Иначе два механизма переноса одного и того же; nullable — по правилу двухшагового ввода из T-502 (184 существующие задачи) |

(инвариант I-03). Эталон для миграций фазы уже есть в репозитории —
`20250703-add-backlog-column-to-projects.xml` (аддитивно, идемпотентно через `NOT EXISTS`,
явный `<rollback/>`).

**Практическое следствие ADR-022:** T-510…T-519 остаются `NOT_STARTED` до появления цифр.
Исключение — то, чья ценность доказана независимо от платформы: T-518 (закрывает разрывы
G-1…G-9 из аудита T-500) и техдолг TD-028/TD-029.

Поля `rule` перенесены из реестра `PROJECT_RULES.md` один в один — T-107 уже привёл правила
к табличному виду, поэтому миграция «правила → данные» механическая.

## Завершено 2026-07-28: T-502 — инварианты фазы: откат кода и откат схемы не симметричны

Результат — `.ai/PHASE5_INVARIANTS.md`. Кода задача не касалась.

14 инвариантов («что обязано продолжать работать») — каждый со **способом проверки** и
честной отметкой авто/полуавто/ручная. Инвариант без проверки это пожелание, а проект уже
обжигался ровно на этом: правила объявляли гейты, которых не существует (T-106).

**Главный вывод измерен, а не предположен: откат кода и откат схемы не симметричны.**

| Находка | Факт |
|---|---|
| **Liquibase rollback фактически недоступен** | Из 46 changelog-файлов 80 операций авто-откатываемы, но **26 changeSet — нет** (21 `<sql>`, 3 `modifyDataType`, 2 `update`). Явный `<rollback>` — в 3 файлах. `rollback` упадёт на первом необратимом и в проекте **никогда не вызывался** |
| **У backend нет быстрой точки отката** | Фронт сохраняет предыдущую сборку в `*.old` (`deploy.yml:149`); backend пересобирается на месте без тегирования образа — откат = пересборка на VDS с 1 CPU |
| **Гейты не детектируют поломку** | Healthcheck backend — `curl -s` **без `-f`**, да ещё на POST-эндпоинт `/auth/login`: контейнер станет `healthy`, отвечая 500 на всё. Smoke фронта — `200` на `/`, то есть регрессию класса «пропал бэклог» не поймал бы: статика отдаётся, экран пуст → **TD-029** |

Отсюда несущее правило фазы: **план отката не может опираться на откат миграций** — только
на миграции, которые не требуется откатывать. Сформулированы 7 обязательных правил
(аддитивность; явный `<rollback>` для новых миграций; разделение деплоя схемы и кода по
времени, чтобы откат кода не требовал отката схемы; двухшаговый ввод обязательных полей —
прямо касается T-515/T-516 при 184 существующих задачах; дефолт, сохраняющий поведение
существующего проекта — T-519/T-510; дамп БД перед миграцией силами владельца).

Риски расписаны по всем 9 задачам фазы. Отмечено, что **T-518 — единственная задача,
меняющая существующее поведение, а не добавляющая новое** (затрагивает 19 файлов через
`useProjectData`), поэтому обязана идти отдельным PR — иначе откат перестанет быть точечным.
Единственная не-аддитивная миграция в планах — уникальность `Project.code` (G-5 из T-500);
сейчас проект один, конфликтов нет, момент удобный.

**До начала реализации фазы** стоит закрыть TD-029 и усилить smoke-проверку: сейчас план
отката держится на гейтах, которые объявят сломанный релиз успешным.

## Завершено 2026-07-28: T-501 — аудит доставки правил: заявленный канал сломан, крупнейший не описан

Результат — `.ai/RULES_DELIVERY_AUDIT.md`. Кода задача не касалась.

**Правила доходят пятью каналами, и файловый — не самый объёмный:**

| Канал | Объём | Надёжность |
|---|---|---|
| `CLAUDE.md` (автоматически) | 15.7 КБ | высокая |
| `.ai/*.md` по инструкции | 223 КБ | **средняя — см. ниже** |

**Заявленный канал физически не выполняется.** `CLAUDE.md` предписывает первым делом

пометкой о превышении лимита. Половина файла не доехала, и об этом никто не знал. Файл
растёт монотонно: 121 КБ (27.07) → 152 КБ (28.07), **+31 КБ за два дня**, и занимает **64%**
стартового контекста — при том что на старте из него нужны четыре вещи: активная задача,
последние изменения, риски, следующие шаги.

**Крупнейший канал не описан нигде.** 762 комментария вида «ТП-176: форма списка спринтов
проверяется на границе — сломанный ответ даёт error-состояние, а не краш доски» — это самый
эффективный вид доставки: правило приезжает вместе с кодом, который собираются менять, и
объясняет, почему здесь сделано именно так. Ни `CLAUDE.md`, ни `PROJECT_RULES.md`, ни
`RULES_TAXONOMY.md` его не упоминают.

**Правила привязаны к одному вендору:** ни `AGENTS.md`, ни `.cursorrules`, ни
`copilot-instructions.md` — ничего. Смена агента = потеря инженерной памяти (обоснование
T-514).

**Что должно стать данными:** чекпоинт (состояние + журнал), реестр задач (уже дублирует
доску WorkTask и синхронизируется вручную), техдолг, реестр правил. Важное следствие: T-107
уже привёл правила к табличному виду с полями — **миграция «правила → данные» не требует
переосмысления, только переноса**. Но крупнейший выигрыш даёт не она, а чекпоинт: 152 КБ →
четыре поля на старте.

**Что сделано по итогам (и что отвергнуто).** Первой редакцией аудита рекомендовалось
разрезать чекпоинт на активную часть и архив по месяцам. По требованию владельца решение
перепроверено отдельным проходом и **отвергнуто**: оно не устраняет рост, а переносит его
(активная часть растёт так же, удержание требует ручного ритуала после каждой задачи —
опора на дисциплину, чья ненадёжность задокументирована в TD-027 и T-106); ось разреза по
времени неверна (нужно «актуальное», а не «свежее» — уроки TD-021 актуальны всегда);
и проблема решается дешевле, потому что файл отсортирован «новое сверху» и первые 200 строк
уже дают 5 последних задач. Плюс архитектурный довод: сам аудит заключает, что чекпоинт
должен стать данными, — резать файлы значит вкладываться в структуру, которую Фаза 5
упраздняет.

**Принято вместо:** исправлена **инструкция**, а не файл (`CLAUDE.md §Старт сессии`).
Состояние теперь берётся из `TASK_REGISTRY.md` (активная задача, зависимости) и
`TECH_DEBT.md` (риски), чекпоинт читается частично и объявлен журналом «почему»; архивация
переведена в гигиену по порогу (~200 КБ), а не в обряд после каждой задачи. `K-40` закрыт
без структурных изменений и без работы, которую пришлось бы переделывать.

**Осталось нерешённым (кандидат в задачу класса T-107):** всё, что инструкция обещала найти
в чекпоинте, уже существует структурированно в реестре задач и реестре долга — чекпоинт
пересказывает это прозой. Корневая проблема не в размере файла, а в трёх файлах,
описывающих одно состояние в трёх формах.

## Завершено 2026-07-28: T-500 — аудит мультипроектности: разрыв ровно один, но корневой

Результат — `.ai/MULTIPROJECT_AUDIT.md`. Кода задача не касалась.

**Хорошая новость: модель уже мультипроектная.** Изоляция данных на бэкенде корректна —
`Project` разделяет задачи, спринты, статусы, встречи и права; каждый проектный запрос
проверяет членство через `CheckerUtil`; назначить исполнителем не-участника нельзя; ключи
React Query содержат `projectId`, протечки кэша между проектами нет. Девять областей
работают на N проектов без единой правки.

**Разрыв — не в модели, а в способе выбора проекта.** «Текущий проект» это не параметр
URL, а серверное поле `User.last_project_id`, которое переписывает **обычный GET**:
`ProjectsService.getProjectData` (`:135`) на каждое чтение данных проекта делает
`setLastProjectId` + `flush`. Фронтенд опирается на этот побочный эффект как на механизм —
«переключение проекта» реализовано как мутация, вызывающая тот же `GET /projects/{id}`.

Из одного этого решения вытекает большинство найденного:

| # | Разрыв |
|---|---|
| G-1/G-2/G-3 | Проект живёт на сервере, а не в URL. Доска `/main` — единственный раздел без `projectId`, то есть не deep-link. Две вкладки с разными проектами невозможны: списки опрашиваются каждые 15 с и первая вкладка уедет за второй. Открытие бэклога другого проекта молча меняет текущий проект |
| G-4/G-5 | `/task/$code` резолвится в текущем проекте, а `Project.code` (префикс кодов) **не имеет ограничения уникальности ни в БД, ни в сервисе** — два проекта могут иметь префикс `ТП`, и `ТП-236` будет существовать в обоих |
| G-6 | Уведомление хранит `projectId` и использует его для встреч, но задачу открывает только по коду — уведомление из другого проекта даст 404 |
| G-8/G-9 | `last_project_id` не сбрасывается при удалении проекта (пользователь остаётся «в» удалённом); открытая карточка задачи переживает переключение проекта |

**Отдельно от Фазы 5, актуально уже сейчас — TD-028:** `GET /users/picker` отдаёт **всех
пользователей системы вместе с email**, а не участников проекта, вопреки собственному
комментарию. Это расходится с K-36 (ПДн) и даёт мёртвый выбор в UI: не-участника видно в
списке, но назначить его бэкенд не даст.

**Граница доказательности зафиксирована честно.** У владельца ровно один проект (проверено
вживую), поэтому все мультипроектные сценарии **выведены из кода и не воспроизводились** —
второго проекта не существует, а заводить его в боевых данных ради эксперимента я не стал.
Каждый пункт аудита помечен «проверено вживую» либо «выведено из кода». Именно «один
проект» и маскировал эти разрывы всё время.

**Вход для следующих задач:** порядок работ в T-518 уточнён — снятие побочного эффекта с
`GET /projects/{id}` и перевод доски на `projectId` в маршруте закрывают четыре разрыва
разом; оба пункта архитектурные (K-37) и требуют ADR в T-503. Три вопроса вынесены владельцу
(архивный проект в переключателе, область уникальности префикса кодов, нужно ли вообще
серверное «последний проект»).

## Завершено 2026-07-28: T-107 — правило теперь формулируется один раз

T-106 закрыл симптом (правила врали про механизмы), T-107 — причину. Причиной был дубль:
`CLAUDE.md` (30.9 КБ) и `.ai/PROJECT_RULES.md` (28.5 КБ) пересекались по 17 блокам, при этом
первый загружается автоматически, а второй — по инструкции из него же. Корпус оплачивался
дважды на каждом старте, а одна и та же норма, записанная в двух местах, разошлась при
правках — так и появились противоречия T-106.

**Что нашёл контр-анализ.** Карта дублей из A1 считала блоки одинаковыми по названию, но по
смыслу они разошлись: `§TESTING FIRST` требовал Integration/UI/E2E без оговорок, а
`§QUALITY GATE` — те же проверки с пометкой «если применимо». Механическое слияние незаметно
ужесточило бы одно требование или ослабило другое, то есть воспроизвело бы ровно тот дефект,
который задача закрывает.

**Решение — разделить по триггеру загрузки, а не держать два близнеца:**

| Файл | Роль | Объём |
|---|---|---|
| `CLAUDE.md` | Точка входа: старт сессии, ядро «всегда», конвейер запроса, продуктовые требования, уроки проекта, деплой, профиль (стек и команды) | **15.7 КБ** (было 30.9) |

Каждая формулировка существует **ровно в одном месте**: точка входа ссылается по ID
(`K-27`, `W-03`, `F-01`…) и текст правил не копирует. Точка входа при этом самодостаточна —
работает, даже если реестр не загружен: это защита от регрессии «правила есть, но их никто
не прочитал». Проверяемость закреплена картой «правило → где сформулировано»
(`PROJECT_RULES §9`) и инструкцией, куда класть новое правило.

**Удалённый балласт** (обоснование — `RULES_TAXONOMY §6`): перечисление ролей `SYSTEM MODE`,
дублирующий `PRIMARY OBJECTIVE`, приложение «согласованность правил» (существовало только
из-за дубля — уцелевшее разрешение K-16 ↔ K-17 сохранено примечанием), описание дерева
каталогов как правила.

**Уроки проекта не сокращены, а систематизированы:** девять «Lessons enforced» превратились
в пак `W-01…W-08` + `R-01/R-02` с триггерами, и к ним добавлены два, выведенные из свежих
инцидентов, — **W-06** (молчаливый отказ недопустим: половина закрытого в июле долга
отказывала беззвучно) и **W-08** (расширение перечисления на бэкенде аддитивно, фронтенд
деградирует к дефолту, а не бросает — иначе обнуляется целый экран).

**Проверка:** 0 дубликатов ID; 0 битых ссылок (26 из точки входа, 59 внутри реестра); 38

## Завершено 2026-07-27: TD-019 «JWT-секрет только из окружения» — закрыта активная уязвимость прода (PR #186)

Найдено при разборе «что делать дальше» после ТП-212 и подтверждено фактами:
`spring.app.jwtSecret` был захардкожен в `application.yml`, репозиторий
**публичный**, а на проде значение **ничем не переопределялось**

войти под любым пользователем, включая администратора. Взлом не требовался —
достаточно было чтения репозитория.

- **Код:** `jwtSecret: ${JWT_SECRET:}` + `JwtUtils#initSecret` (fail-fast):
  прежнее скомпрометированное значение отвергается в ЛЮБОМ профиле (чтобы фикс
  нельзя было откатить одной переменной); пустой секрет вне `local`/`test`
  останавливает запуск; короткий (<256 бит) или не-base64 — тоже отказ на
  старте, а не невнятная ошибка при первом логине; в `local`/`test` секрет
  генерируется на запуск, поэтому «склонировал и запустил» работает без
  настройки окружения.
- **Прод:** новый секрет сгенерирован на сервере (`openssl rand -base64 48`),
  записан в `.env.vds` (значение нигде не печаталось), задеплоен.
- **Проверено вживую:** токен, подписанный утёкшим ключом, отвергается (401);
  повторный логин и новые токены работают (200); голосовые режимы ТП-212 после
  деплоя работают без регрессий. Все прежние сессии разлогинены — ожидаемое и
  желательное следствие.
- Тесты: backend 199/199 (+8 регресс-тестов на новую защиту).

**Осталось открытым:** TD-021 (автоматизации деплоя нет; секретов

**Что показала живая проверка и что исправлено:**

## Доделано 2026-07-26: ТП-195 (добор) — тост «Открыть» открывает МОДАЛКУ, а не страницу

**Пропущенный при первом заходе критерий приёмки** (найден пользователем на
проде): «Тост "Открыть", клик с доски и из списка открывают задачу одинаково».
`useCreateTask.onSuccess` вёл `router.navigate({ to: '/task/$code' })` — то есть
задача, созданная через форму, открывалась ПОЛНОЙ СТРАНИЦЕЙ, а с доски —
модалкой. Ровно та неконсистентность, ради которой заведена ТП-195; первый заход
починил смежное (guard на странице), а саму точку входа не тронул.

- **Фикс:** `useCreateTask` открывает `TaskCardModal` по коду созданной задачи
  (`NiceModal.show` — глобальная функция со своим диспатчем, работает из мутации
  вне React-дерева, где router-хуки недоступны; урок ТП-39). Карточка тянется
  динамическим `import()` — разрывает цикл
  `useCreateTask → TaskCardModal → … → useCreateTask` и не тащит её в бандл формы.
- **Постоянный репро-тест** `features/task/__tests__/createTaskToastOpen.test.tsx`
  (правило post-mortem): «Открыть» вызывает `NiceModal.show({taskCode})` и НЕ
  вызывает `router.navigate`. Проверено, что тест краснеет при откате фикса.
- **Проверено вживую** (локальный backend + чистая БД): создание задачи → тост
  «Создана задача TC-2» → «Открыть» → URL остаётся `/main`, открыта модальная
  карточка TC-2; вкладка «Связи» внутри неё — 0 ошибок в консоли.
- **Осталось той же природы (НЕ трогал, отдельное решение):** голосовая команда
  «открой задачу» (`useVoiceServices.navigate` → `voiceNavPath` → `/task/$code`)
  по-прежнему открывает полную страницу. Прямой URL `/task/CODE` страницей —
  это by design (deep-link, Option B тикета).

## Завершено 2026-07-26: ТП-195 «Карточка задачи — единый переиспользуемый компонент» (ветка `claude/tp-195-tp-210-ecbb11`)

**Анализ показал: дублирования уже нет.** `TaskCardContent` (features/task) уже
единственная реализация полей/статуса/вложений/комментариев/связей/истории —
используется и в `TaskCardModal` (NiceModal, доска/список/уведомления), и в
`EditTaskPage` (полная страница `/task/$code`, deep-link). Создание (`CreateTaskContent`
+ `TaskFormFields`) тоже делит компоненты с редактированием. Реальный пробел был не в
полях, а в **паритете поведения между модалкой и страницей**:

- **Фикс (регрессия отн. модалки):** `EditTaskPage` не пробрасывал `guardRef` —
  несохранённые изменения (ТП-34) никак не защищались при уходе со страницы (сайдбар,
  «Назад», связанная задача). Добавлен `useBlocker` (TanStack Router, `withResolver`) в
  `EditTaskPage`, полностью аналогичный `TaskCardModal`. Диалог подтверждения вынесен в
  общий `UnsavedChangesGuardDialog` (features/task) — используется в обоих контейнерах
  (DRY, не два текста одной и той же логики).
- **Проверено вживую** (поднят локальный backend на изолированной БД postgres:16 —
  общий docker-compose сломан на `postgres:latest`, см. TD-020): диалог появляется и в
  модалке (крестик), и на странице (клик по сайдбару/связанной задаче) при dirty-форме;
  «Отменить изменения» откатывает (подтверждено запросом к API — заголовок НЕ сохранён);
  «Сохранить изменения» сохраняет и только потом пускает переход (подтверждено на доске).
  Прямой URL `/task/CODE` (deep-link) рендерит ту же карточку.
- **Отклонённый вариант (URL-синхронизация модалки, ADR-заметка):** тикет предлагал как
  рекомендуемый паттерн Linear — модалка меняет URL на `/task/CODE`, не покидая фоновую
  страницу. Проверено по исходникам `@tanstack/router-core`: route masking требует
  РЕАЛЬНОЙ навигации на другой матч маршрута (масштаб — отдельный вложенный роут на
  КАЖДУЮ фоновую страницу, с которой можно открыть модалку — доска/спринт/список/
  уведомление с любой страницы). Инвазивно и не оправдано ради одной задачи — выбран
  Option B тикета («оставить прямой /task/ID страницей, но на одном компоненте»,
  дубль устранён в любом случае).
- **Отклонённая попытка (SPA-навигация в «Связях»):** пробовал заменить `TaskLinks`'
  `<a href>` на router-`<Link>`, полагаясь на комментарий router.tsx «ТП-131 чинит
  NiceModal вне роутера». Проверено вживую: `<Link>`/`useLinkProps` всё равно падает
  (`useRouterState`: `Cannot read properties of null, reading '__store'`) при рендере
  внутри `TaskCardModal`, несмотря на формальную вложенность в RouterProvider — старый
  комментарий ТП-39 был не полностью устранён для конкретно этого хука. Возвращено к
  `<a href>` (полная перезагрузка) с уточнённым комментарием, объясняющим РЕАЛЬНУЮ
  причину. Урок: не полагаться на комментарий/чужой вывод — обязательно проверять вживую.
- Тесты: 449/449 (Vitest), включая постоянные регресс-тесты ТП-201/ТП-172
  (`taskCardDescriptionRoundtrip`, `taskCardOutsideRouter` — рендер `TaskCardModal` БЕЗ
  RouterProvider не должен падать; это ограничение учтено в реализации гварда —
  `EditTaskPage`'s `useBlocker` используется только там, где RouterProvider гарантирован).
  Lint 0, `tsc -b && vite build` — зелёные.
- **Побочная находка (не в скоупе, задокументирована отдельно):** TD-020 —
  `docker-compose.yml` локального окружения сломан из-за нефиксированного
  `postgres:latest` (теперь резолвится в 18+, несовместимую схему volume).
