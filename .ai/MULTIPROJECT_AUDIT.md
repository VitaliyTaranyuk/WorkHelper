# T-500 — аудит фактической мультипроектности

> Дата: 2026-07-28. Задача: T-500 (ТП-221). Код не изменялся — это аудит.
> Вход для T-502 (инварианты и риски) и T-518 (мультипроектная навигация).

## Статус доказательности

Приложение **никогда не эксплуатировалось более чем на одном проекте**: у владельца
(`test2@mail.ru`) на 2026-07-28 ровно один проект — «WorkTask» (проверено вживую через меню
проекта на проде). Поэтому:

- **Проверено вживую** — только поведение на одном проекте: доска, список задач, спринт,
  карточка, уведомления работают.
- **Выведено из кода** — всё, что касается двух и более проектов. Второго проекта не
  существует, воспроизвести сценарии было не на чем, а заводить проект в боевых данных
  владельца ради эксперимента я не стал.

Каждый пункт ниже помечен соответственно. Это разделение — не формальность: половина
разрывов невидима именно потому, что «один проект» маскирует их полностью.

---

## 1. Итог одним абзацем

Изоляция данных **на бэкенде реализована корректно**: `Project` разделяет задачи, спринты,
статусы, встречи и права, каждый запрос проверяет членство через `CheckerUtil`. Разрыв
находится **не в модели, а в способе выбора проекта**: «текущий проект» — это не параметр
URL, а серверное поле `User.last_project_id`, которое молча меняется обычным `GET`. Из этого
единственного решения вытекает большинство найденных проблем.

## 2. Что уже работает на N проектов

| Область | Состояние | Основание |
|---|---|---|
| Модель данных | **работает** | `Project` ↔ `TaskModel`, `Sprint`, `TaskStatus`, `Meeting`, `UsersProject` — всё привязано к проекту |
| Проверка доступа | **работает** | `CheckerUtil.findAndCheckProjectUserData` → `checkHasProjectForUser` на каждом проектном запросе |
| Назначение исполнителя | **работает** | `findAndCheckActiveUser(userId, project)` отвергает не-участника |
| Статусы задач | **работает** | `TaskStatus.project` + ограничение `unique_code_project`; у каждого проекта свой набор колонок |
| Расширенные права | **работает** | `unique_project_user_extended_permission` — права в разрезе проекта |
| Календарь | **работает** | `GET/POST /meetings/project/{projectId}` — scope в пути |
| Коды задач на бэкенде | **работает** | `findByCodeAndProject(code, project)` — код резолвится в пределах проекта |
| Кэш React Query по задачам и спринтам | **работает** | ключи содержат `projectId`: `['sprints', projectId, …]`, `['tasks', projectId, …]` |
| Список проектов | **работает** | `getAllUserProjects` отдаёт все проекты пользователя, фильтрует `DELETED`, сортирует стабильно |

## 3. Карта разрывов

| # | Область | Оценка | Что происходит |
|---|---|---|---|
| **G-1** | Выбор текущего проекта | **протекает** | «Текущий проект» — серверное состояние `User.last_project_id`, а не URL |
| **G-2** | `GET /projects/{id}` | **протекает** | GET-запрос **мутирует** состояние пользователя (побочный эффект) |
| **G-3** | Доска `/main` | **отсутствует** | Единственный раздел без `projectId` в URL — не deep-link |
| **G-4** | Deep-link задачи `/task/$code` | **протекает** | Код резолвится в текущем проекте; ссылка неоднозначна |
| **G-5** | Уникальность `Project.code` | **отсутствует** | Нет ограничения БД и нет валидации в сервисе |
| **G-6** | Уведомления → задача | **протекает** | `projectId` в уведомлении есть, но при открытии задачи не используется |
| **G-7** | Picker пользователей | **протекает** | Отдаёт всех пользователей системы с email, а не участников проекта |
| **G-8** | Удаление проекта | **протекает** | `last_project_id` не сбрасывается — пользователь остаётся «в» удалённом проекте |
| **G-9** | Модалки при переключении проекта | **протекает** | Открытая карточка задачи переживает смену проекта |
| **G-10** | Архивный проект | **работает с оговоркой** | `ARCHIVED` остаётся в списке проектов (вероятно, намеренно), `DELETED` — фильтруется |

## 4. Разрывы детально

### G-1/G-2/G-3 — корневой разрыв: проект живёт на сервере, а не в URL

*Выведено из кода.*

`ProjectsService.getProjectData` (`services/ProjectsService.java:132-139`) на каждый вызов
делает `user.setLastProjectId(projectId); userRepository.flush();`. Этот метод обслуживает
`GET /projects/{projectId}`. То есть **чтение данных проекта переписывает глобальное
состояние пользователя**.

Фронтенд опирается на это как на механизм:

- `useProjectData.useActiveProjectInfo` вызывает `getProjectData` в обычном `useQuery` — то
  есть любой рендер, которому нужны данные проекта, меняет серверное состояние;
- `useChangeProject` — «переключение проекта» реализовано как мутация, которая вызывает тот
  же `GET /projects/{id}` ради его побочного эффекта;
- `MainPage` берёт проект **только** из `useProjectData()` (`page/main/MainPage.tsx:12`),
  никаких параметров маршрута не читает.

**Следствия:**

1. **Две вкладки с разными проектами невозможны.** Открытие проекта B во второй вкладке
   перезапишет `last_project_id`; первая вкладка после ближайшего рефетча покажет чужой
   проект — а списки опрашиваются каждые **15 секунд**
   (`LISTS_POLL_INTERVAL_MS`, `features/task/query/pollingConfig.ts:12`).
2. **Доску нельзя передать ссылкой** — `/main` у получателя откроет его собственный
   последний проект. Список задач, спринт и календарь при этом deep-link'абельны.
3. **Простое открытие `/project/{B}/backlog` меняет глобальный «текущий проект»** — потому
   что страница запрашивает данные проекта B, а это сдвигает `last_project_id`. Пользователь
   заглянул в бэклог другого проекта — доска молча уехала следом.

### G-4/G-5 — deep-link задачи неоднозначен

*Выведено из кода.*

Бэкенд корректен: `GET /tasks/{projectId}/code/{code}`, поиск через
`findByCodeAndProject`. Но маршрут фронтенда — `/task/$code` **без проекта**, и
`useTaskByCode({projectId, taskCode})` подставляет текущий проект.

Усугубляется тем, что `Project.code` (префикс кодов задач) **ничем не ограничен**:
в модели это `@Column(nullable = false)` без `unique`, в `ProjectsService` проверки нет,
в миграциях уникальных ограничений на `project.code` не заведено. Два проекта могут
одновременно иметь префикс `ТП`, и тогда `ТП-236` существует в обоих.

Итог: ссылка `/task/ТП-236` открывает **разные задачи у разных людей** — или 404, если у
получателя другой текущий проект.

### G-6 — уведомления знают проект, но не пользуются им

*Выведено из кода.*

`Notification` хранит `project_id` (`models/tables/Notification.java:45-46`), и
`NotificationBell` использует его для встреч:

```
if (n.meetingId && n.projectId) navigate({ to: '/project/$projectId/calendar', params: { projectId: n.projectId } })
```

А для задач — `openTaskCard(n.taskCode)`, только код. Уведомления при этом выбираются
`findByRecipientIdOrderByCreatedAtDesc(userId)`, то есть **по пользователю через все
проекты**. Значит уведомление о задаче из проекта B, открытое при текущем проекте A, даст
404 — или чужую задачу, если префиксы совпали (G-5).

Данные для правильного поведения уже есть; не задействован один аргумент.

### G-7 — picker отдаёт всех пользователей системы

*Выведено из кода. Актуально уже сейчас, не только при мультипроектности.*

`UserService.pickerSearch` (`services/UserService.java:160-174`) фильтрует по активности,
`isSystem` и наличию username — **но не по проекту**: источник `userRepository.getUsers()`.
При этом `UserPickerDto` содержит **email**.

Комментарий над эндпоинтом утверждает «доступен всем участникам проекта», что читается как
scope, но scope'а нет. Последствия:

- любой участник любого проекта видит имена и **email всех пользователей системы** — это
  расходится с **K-36** (ПДн: минимизировать, ограничивать доступ по ролям);
- в выпадающем списке исполнителей появляются люди, назначить которых нельзя: бэкенд
  отвергнет их через `findAndCheckActiveUser` — мёртвый выбор в UI (**K-32**).

### G-8 — удалённый проект остаётся текущим

*Выведено из кода, вживую не воспроизводилось (потребовало бы удалить боевой проект).*

`deleteProject` помечает проект `DELETED`, но `last_project_id` пользователя не трогает.
Фронт после удаления инвалидирует `['userProjects']` и `['activeProject']`, перезапрашивает
`/projects/last` и получает **id удалённого проекта**. `getProjectData` его отдаёт:
`findProject` ищет по id без фильтра статуса, `checkHasProjectForUser` проходит — членство
никуда не делось.

Ожидаемое поведение: после удаления текущего проекта пользователь должен оказаться в другом
своём проекте или в пустом состоянии.

### G-9 — модалка переживает смену проекта

*Выведено из кода.*

`ProjectSwitcher.switchTo` вызывает `changeProject.mutate` и `navigate({ to: '/main' })`.
Ни закрытия модалок, ни `NiceModal.remove` при этом нет. Карточка задачи живёт вне
роутера (**R-02**), поэтому навигация её не размонтирует: над доской нового проекта
останется открытая задача старого, и её сохранение уйдёт в прежний `projectId`.

## 5. Граничные сценарии (проверка A2)

| Сценарий | Результат |
|---|---|
| Пользователь без проектов | `useActiveProjectId` → `activeProjectData?.id \|\| userProjects[0]?.id` → `undefined`; `activeProject = null`, запросы отключены `enabled`. Доска не падает, но `onReorder` содержит `activeProject!.id` — non-null assertion, достижимая только при наличии доски. **Отдельного empty-state «у вас нет проектов» не найдено** — требует проверки вживую |
| Пользователь в нескольких проектах | Основной источник разрывов G-1…G-9 |
| Переключение при открытой модалке | G-9 |
| Кэш между проектами | **Протечки нет**: ключи задач/спринтов содержат `projectId`. Исключение — `['notifications']` (глобальные по дизайну) и `['userPicker', q]` (глобальный по факту, см. G-7) |
| Коды задач | G-4/G-5 |
| Архивный проект | Остаётся в списке (`getAllUserProjects` фильтрует только `DELETED`). Похоже на намеренное решение; поведение доски для архивного проекта не проверялось |
| Удалённый проект | G-8 |

## 6. Что это значит для Фазы 5

Главный вывод: **мультипроектность не нужно «добавлять» — её нужно достроить в одном
месте.** Модель, права и изоляция данных уже готовы; неявным остаётся только выбор
проекта. Смена `last_project_id` на `projectId` в маршруте закрывает G-1, G-2, G-3, G-4 и
делает G-8/G-9 почти тривиальными.

Порядок, вытекающий из аудита (уточняет T-518):

1. **Убрать побочный эффект из `GET /projects/{id}`** — это одно изменение снимает
   G-2 и делает возможным всё остальное. Обратно совместимо: явную установку текущего
   проекта вынести в отдельный endpoint, если она вообще нужна.
2. **Ввести `projectId` в маршрут доски** (`/project/$projectId/board` или редирект
   `/main` → последний проект) — закрывает G-1 и G-3.
3. **`projectId` в deep-link задачи** и `Notification.projectId` при открытии карточки —
   G-4 и G-6.
4. **Уникальность `Project.code`** — G-5, требует миграции и решения о существующих данных
   (сейчас проект один, конфликтов нет — момент удобный).
5. **Scope picker'а по проекту** — G-7; это ещё и вопрос ПДн, стоит закрыть независимо от
   Фазы 5.
6. **Сброс `last_project_id` при удалении проекта и закрытие модалок при переключении** —
   G-8, G-9.

Пункты 1 и 2 — архитектурное изменение (**K-37**), требуют ADR в T-503.

## 7. Открытые вопросы для владельца

1. **Архивный проект в списке проектов** — оставлять? Сейчас `ARCHIVED` виден наравне с
   активными, отличить его в переключателе нельзя.
2. **Уникальность префикса кодов задач** — глобальная (`ТП` занят навсегда) или в пределах
   владельца/воркспейса? От этого зависит миграция в T-503.
3. **Нужен ли вообще «последний проект»** как серверное состояние после перехода на URL —
   или достаточно редиректа с `/` на последний открытый проект, хранимый на клиенте.
