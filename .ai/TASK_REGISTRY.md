## ПРОТОКОЛ ИСПОЛНЕНИЯ ЗАДАЧИ

> Обязателен для всех задач фаз 1 и 5. Порядок фиксированный, реализация — последней.
> Формулируется здесь один раз; в задачах указывается только отклонение от протокола.

| Этап | Что делается | Выход | Правки кода |
|------|--------------|-------|-------------|
| **A1 — Анализ** | Собрать факты из кода, истории, конфигов и запусков. Определить: что есть сейчас, что затрагивается, радиус поражения, какие сценарии зависят | Список фактов со ссылками `файл:строка`; карта затронутого; список рисков | Запрещены |
| **A2 — Контр-анализ** | Отдельным проходом оспорить A1: что упущено, где предположение выдано за факт, какие граничные случаи не рассмотрены, что сломается у существующих данных и пользователей | Перечень проверенных и **отвергнутых** гипотез; найденные пробелы A1; блокеры | Запрещены |
| **D — Решение** | Зафиксировать выбранный вариант и альтернативы, критерии приёмки, план отката. При архитектурном изменении — ADR в `.ai/ARCHITECTURE.md` | Решение + критерии приёмки + план отката | Запрещены |
| **I — Реализация** | Код строго в границах D | Изменения в коде и тестах | Разрешены |
| **V — Верификация** | Тесты → сборка → production build; для видимых изменений — проверка на развёрнутом окружении со ссылкой | Отчёт о проверке | Только фиксы найденного |

**Гейты:**
- `I` не начинается, пока `A2` не выполнен и все выявленные им блокеры не закрыты в `D`.
- `A2` выполняется **как отдельный проход**, а не дописывается к A1: его задача — найти ошибку в A1, а не подтвердить его.
- Если `A2` не нашёл ни одного пробела — это признак формального прохода; зафиксировать явно, что именно проверялось.
- Расхождение «документация ↔ реальность», найденное на любом этапе, фиксируется в `.ai/TECH_DEBT.md` немедленно, даже если не относится к задаче.

## Развёрнутые описания задач

### T-106 — Устранить расхождения «правило ↔ реальность»

Найдено при сплошной проверке 2026-07-28. Три расхождения, все — правила описывают
несуществующий механизм или противоречат друг другу:

1. **Покрытие.** `CLAUDE.md` §TEST COVERAGE: 80% — «ориентир, не блокирующий gate».
   `PROJECT_RULES.md` §TESTING POLICY: «минимальное покрытие ≥80%, порог проверяется в
   сборке/CI (backend — JaCoCo, frontend — Vitest/c8)». Фактически: JaCoCo в
   `backend/build.gradle` отсутствует, coverage-провайдера во фронтенде нет, шага покрытия
   в CI нет. Упоминание механизмов — ложное утверждение внутри файла правил.
2. **Ветка `main`.** `CLAUDE.md` §GITHUB WORKFLOW допускает исключение «критический hotfix»;
   `PROJECT_RULES.md` §GIT WORKFLOW запрещает без исключений. Фактически: 191 merge-коммит,
   прямых коммитов после 21.06.2026 нет ни одного; защита ветки на GitHub **не включена**.
3. **Состав CI.** `PROJECT_RULES.md` §CI/CD объявляет обязательными Lint, Static Analysis,
   Unit, Integration, Build, Dependency Security Scan. Фактически `backend-ci.yml` = build +
   test, `frontend-ci.yml` = lint + test + build; статанализа и security scan нет нигде.

**A1:** подтвердить каждое расхождение первичной проверкой (файлы сборки, workflow,
API защиты ветки, история `main`). **A2:** проверить, нет ли других правил, описывающих
несуществующие механизмы — сплошным проходом по обоим файлам. **D:** по каждому пункту
решить: привести текст к реальности или завести задачу на реальность. **I:** правка текста
правил. **V:** ни одно утверждение в правилах не описывает того, чего нет.

Связанные: T-102 (защита ветки), T-104 (статанализ), T-105 (покрытие), T-303 (security scan).
Задача закрывает **текст**; реальность закрывают связанные задачи.

**Итог (закрыта 2026-07-28, PR #201).** A2 нашёл четвёртое расхождение того же класса,
пропущенное в описании: `§CI/CD` объявляет обязательными **Integration Tests**, которых не
существует ни одного (0 классов с `@SpringBootTest`/Testcontainers на 23 тестовых класса),
при этом `backend-ci.yml` поднимает сервис `postgres:16`, которым не пользуется ни один тест.
То же расхождение оказалось и в `CLAUDE.md §CI/CD`, а не только в `PROJECT_RULES.md`.

Принцип правки: **разделить намерение и механизм**. Ни одно требование не ослаблено —
менялись только утверждения о том, чем требование обеспечено. Где механизма нет, правило
это признаёт и ссылается на задачу (T-101/T-102/T-104/T-105/T-303).

Найдено побочно и зафиксировано немедленно (требование протокола): **TD-027** — хуки
lefthook (`pre-commit → lint`, `pre-push → build`) объявлены, но не установлены, то есть
локальный `QUALITY GATE` не автоматизирован ничем; **TD-003** переформулирован — долг не в
«прямых push» (их нет с 21.06.2026), а в отсутствии защиты ветки как механизма.

### T-107 — Дедупликация и нормализация правил

`CLAUDE.md` (26.7 КБ) и `PROJECT_RULES.md` (26.1 КБ) дублируют друг друга по 17 блокам;
`CLAUDE.md` загружается автоматически, а `PROJECT_RULES.md` — по инструкции из него же.
Оба противоречия T-106 — прямое следствие дубля.

**A1:** сверить блоки построчно, зафиксировать все расхождения формулировок.
**A2:** проверить, что при слиянии не теряется ни одно уникальное требование; отдельно
проверить блоки, которые выглядят дублем, но различаются по смыслу.
**D:** решить, что остаётся точкой входа, а что источником; назначить каждому правилу
уровень (ядро / пак / профиль) и условие загрузки по `.ai/RULES_TAXONOMY.md`.
**I:** переписать оба файла. **V:** каждое правило встречается один раз; уникальные
требования не потеряны (сверка по списку из A1).

### T-500 — Аудит фактической мультипроектности

**A1:** пройти по backend и frontend и составить карту: где `Project` уже полноценно
разделяет данные, где проект выбирается неявно, где предполагается «текущий/единственный».
Проверить: навигацию и роутинг, сайдбар, права (`UsersProject`, `ExtendedPermission`),
статусы задач (`TaskStatus` привязан к проекту), уведомления, календарь, голосовой контекст.
**A2:** отдельным проходом проверить сценарии, которые обычно ломаются при мультипроектности:
переключение проекта при открытой модалке, кэш запросов между проектами, коды задач
(`Project.code` + `taskCounter`), архивный/удалённый проект, пользователь без проектов,
пользователь в нескольких проектах. Зафиксировать, какие из них проверены на живом приложении.
**Выход:** карта разрывов с оценкой каждого (работает / протекает / отсутствует).

### T-502 — Инварианты и риски эволюции

Ключевая задача фазы: явно записать, **что обязано продолжать работать**, чтобы развитие
не сломало текущее. Минимум: существующие проекты и их задачи; коды задач; права и
приглашения; голосовой модуль; деплой и сборка; текущие 449+ фронтенд-тестов.

**A1:** составить список инвариантов и способ проверки каждого.
**A2:** для каждого инварианта ответить, каким изменением фазы 5 он может быть нарушен;
отдельно — что произойдёт с данными на проде при каждой планируемой миграции.
**D:** план отката фазы целиком и по каждой задаче; правило «только аддитивные миграции».

### T-519 — Kanban-режим проекта: развилка

Существующая задача T-156 предполагает **удаление** спринтов (TD-005..008), но помечена
«после согласования разрушающих миграций». Предлагаемая альтернатива: не удалять, а сделать
спринты необязательными через режим проекта — дешевле, обратимо, не ломает данные и тесты.

Решение принимает владелец. **A1** — оценить обе стоимости; **A2** — проверить, что режим
не оставляет мёртвого UI (признак незавершённости по правилам); **D** — зафиксировать выбор
и, если выбран режим, закрыть T-156 как отменённую с обоснованием.
