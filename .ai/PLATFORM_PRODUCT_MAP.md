# Продуктовая карта платформы: что выкидываем, что становится ядром, что проверяем

> Дата: 2026-07-28. Статус: продуктовый дизайн, реализация не начата.
> Основание: [MARKET_RESEARCH_PLATFORM_2026.md](./MARKET_RESEARCH_PLATFORM_2026.md).
> Все решения ниже выводятся из зафиксированных там данных; там, где решение
> принято на допущении, это помечено как **[допущение]**.

---

## 0. Одно предложение

Платформа — это **переносимая между проектами инженерная память**, которая делает
работу агента на существующей кодовой базе дешевле и предсказуемее и учится на
повторах пользователя. Не борд. Не ещё один spec-фреймворк.

---

## 1. Что выкидываем — и почему

| Выкидываем | Почему | Во что превращается |
|---|---|---|
| Компиляция правил под N агентов **как фича** | AGENTS.md — стандарт (60k+ репо, читают все крупные агенты); rulesync и аналоги бесплатны | Интеграционная деталь. Пишем в AGENTS.md, не изобретаем формат |
| Борд/канбан **как ценность** | GitHub Agent HQ сверху, Linear/Jira снизу; в оркестрации уже есть банкрот (Bloop) | UI остаётся, но за него не платят. Задачи можно держать в GitHub Issues |
| Тяжёлый спек-процесс на каждую задачу | Scott Logic: 10x медленнее, 2577 строк markdown ради 689 строк кода, без выигрыша качества | Пропорциональность процесса (см. §4) |
| Автогенерация правил агентом без человека | LLM-написанные инструкции: −2% успех, +23% стоимость; человеческие: +4% успех, −35…55% багов | Предложения с доказательствами + обязательный человеческий гейт |
| Хранение кода и знаний проекта в облаке | Продажа в любой сегмент упирается в security review; плюс расходы | Знания в репозитории клиента, в облаке — только телеметрия процесса |
| Обещания «3–10x продуктивности» | Реальность: медиана +7.76%, диапазон 5–15% | Обещаем меньше переделок и меньше токенов, с цифрами |
| Собственный агент / собственная модель | Кошелёк уже занят токенами ($200–600/dev/мес), конкуренция с фронтир-вендорами безнадёжна | BYO agent как принципиальная позиция |

**Главный вывод раздела:** мы убираем из продукта всё, что кто-то уже раздаёт
бесплатно, и всё, что требует конкурировать с GitHub или с вендорами моделей.

## 2. Три столпа, которые остаются

### Столп 1. Переносимая инженерная память

Знание, которое накапливается **у владельца, а не у вендора агента**, и переезжает
между его проектами.

Уровни (как обсуждали, но теперь с обоснованием):

* **Kernel** — инвариантное. Тонкое намеренно: любое правило в ядре платится токенами
  в каждом проекте на каждой задаче.
* **Stack pack** — «React», «Spring», «мобилка». Решает проблему холодного старта:
  клиент получает ценность в первый день, до всякого обучения.
* **Project profile** — в репозитории клиента, включая **контракт возможностей**
  (`test`, `build`, `deploy`, `verify` как именованные операции).

Каждое правило имеет: id, область действия, триггер, **провенанс** (откуда взялось:
человек / промоушен из проекта X / предложение, принятое тогда-то), версию,
статистику применения.

Почему это защищаемо: BugBot учится внутри Cursor и только про ревью; Agent HQ
привязан к GitHub-периметру; spec-фреймворки не переносят уроки между проектами.
Кросс-проектная память, отчуждаемая от вендора агента, — пустое место на карте.

### Столп 2. Экономика контекста

Самая доказуемая часть ценности. Опора: стоимость задачи агента $0.03–$2.60, и
**основная часть счёта — контекстный оверхед**, а не сгенерированный код;
компактификация даёт 30–70% экономии.

Продуктовое выражение — **контекст-бандл под задачу** вместо «прочитай всё»:
задача + релевантный срез архитектуры + только применимые правила + последние
решения по этой области. Остальное — по запросу.

Локальное подтверждение проблемы: `.ai/PROJECT_CHECKPOINT.md` — 128 КБ, читается
в начале каждой сессии.

### Столп 3. Brownfield-first

Все обзоры называют «фундаментальную проблему модификации» главным нерешённым
разрывом: инструменты хороши на greenfield и проваливаются на итеративных изменениях.
Там же сидит и боль (66% — «почти правильно, но не совсем»; churn ×9 у активных
пользователей AI).

Продуктовое выражение:
* **delta-мышление** — описываем что меняется, а не пересказываем систему целиком;
* **карта радиуса поражения** — что сломается от этого изменения;
* «**что уже есть**» перед «что построить» — обязательный шаг против дублирования кода.

## 3. Модель предметной области (концептуально)

Разделение, которое надо заложить в схему с первого дня — потом не пришьётся:

**В репозитории клиента (контент, версионируется вместе с кодом):**
профиль проекта, контракт возможностей, карта архитектуры, ADR, спеки изменений,
уроки проекта, скомпилированный AGENTS.md.

**В платформе (телеметрия процесса, без контента):**
`Workspace → Project (привязка к репо) → Task → Run → Signal → Proposal → Rule → Metric`.

Где `Run` — запись одного прогона агента: какая фаза, сколько токенов, чем кончилось,
сколько итераций до зелёного. `Signal` — наблюдение без содержимого кода.
`Proposal` — кандидат в правило с доказательствами.

Правило разделения простое: **в облаке — форма процесса, в репозитории — суть продукта.**
Это одновременно снимает главное возражение при продаже и оставляет возможность
кросс-клиентского обучения в будущем без переделки схемы.

## 4. Пропорциональность процесса (прямой ответ на критику SDD)

Единственный процесс на все задачи — доказанно вредная идея. Вводим «передачи»:

| Размер | Что запускается | Обоснование |
|---|---|---|
| **XS/S** — правка текста, стиля, локальный баг | Никакой спеки. Контекст-бандл + исполнение + гейт тестов | Накладные расходы SDD масштабируются с размером; мелкие задачи страдают больше всего |
| **M** — фича внутри существующего модуля | Delta-спека: что меняется (добавлено/изменено/удалено) + критерии приёмки + радиус поражения | Delta-подход — единственный, который обзоры признают работающим на brownfield |
| **L/XL** — новый модуль, новая интеграция, архитектурное изменение | Полный конвейер: Intent → Discovery → Spec → Impact → Декомпозиция | Здесь церемония окупается |

Классификатор предлагает передачу, человек может понизить или повысить одним
действием. **Понижение передачи — тоже сигнал для обучения** (систематически
завышаем сложность → калибровать классификатор).

Гейт подтверждения — **ровно один**, после спеки. Не «уточняющие вопросы на каждом шаге».

## 5. Цикл обучения: конкретная механика

Схема: `Сигнал → Детектор → Кандидат → Предложение с доказательствами → Гейт человека
→ Правило с провенансом → Измерение эффекта → Деградация/отзыв`.

Валидация механики: BugBot делает ровно это (генерирует правила из реакций на PR,
продвигает подтвердившиеся, выводит из обращения получающие негатив) — resolution
rate 52% → ~80%.

### Детекторы, которые реально можно построить

| # | Детектор | Сигнал | Предложение |
|---|---|---|---|
| 1 | **Повторяющееся намерение** | Пользователь N раз вручную просит одно и то же («сначала проанализируй рынок», «прогони линт») | Вынести в фазу процесса проекта |
| 2 | **Повторяющийся отказ** | Один и тот же тип падения после N задач (та же проверка, тот же линт-рул) | Правило-предупреждение или шаг в чек-лист |
| 3 | **Повторяющаяся правка ревьюера** | Пользователь одинаково переделывает результат | Кандидат в правило проекта |
| 4 | **Конфликт/дубликат правил** | Два правила пересекаются или противоречат | Слияние, приоритет, удаление |
| 5 | **Правило-балласт** ⭐ | Правило грузится в контекст, но ни разу не изменило поведение за K задач | **Удалить — прямая экономия токенов** |
| 6 | **Контекстный жир** ⭐ | Файл/секция стабильно попадает в бандл и не используется | Выкинуть из бандла |

Детекторы 5 и 6 — самые ценные и никем не сделанные: они конвертируются в деньги
напрямую и работают против естественного дрейфа любых систем правил (правила только
накапливаются и никогда не удаляются). Это же отличает нас от spec-фреймворков,
где корпус документов растёт монотонно.

### Обязательные ограничения

* **Никакого автоприменения.** Система, молча меняющая свои правила, теряет доверие
  необратимо. Плюс есть исследованный класс атак на самоэволюционирующих агентов.
* **Предложение без доказательств не показывается.** Формат: что заметили, на каких
  задачах, что меняем, ожидаемый эффект, как откатить.
* **Отклонение — тоже сигнал**, снижает вес похожих кандидатов.
* **Промоушен по уровням**: проект → (подтвердилось в N проектах и не стек-специфично)
  → stack pack → kernel. Обратное движение обязательно.
* **Версии ядра пинятся per-project**, обновление осознанное, с changelog и откатом.

## 6. Метрики: одновременно продукт и внутренний критерий

Показываем пользователю и используем как критерий принятия правил:

| Метрика | Зачем | Бенчмарк для сравнения |
|---|---|---|
| Токены и стоимость на задачу | Прямая экономия | $0.03–$2.60 за задачу по индустрии |
| **Rework rate** (доля кода, переписанного за 2 недели) | Главная боль | 5.7–7.1% по индустрии; ×9 у активных пользователей AI |
| Доля задач, прошедших без возврата | Предсказуемость | 66% жалуются на «почти правильно» |
| Время intent → merge | Скорость всего цикла | — |
| Итераций до зелёных тестов | Качество контекста | — |
| «Правила, которые окупились» | Доверие к обучению | — |

Без базовой линии продукт недоказуем. **Измерение — это MVP-0, а не «потом».**

## 7. Минимальная проверяемая версия

Формулируем не как список фич, а как гипотезы с критериями провала.

### MVP-0 — Инструментирование (проверяем: измеримо ли вообще)
Собрать метрики §6 на WorkTask как есть, без изменений процесса. 2–3 недели данных.
**Провал:** метрики не собираются достоверно → вся ценность недоказуема, идею
переосмысливать.

### MVP-1 — Контекст-бандл + детекторы 5 и 6 (проверяем: есть ли экономия)
Собирать контекст под задачу вместо чтения всего; находить балласт.
**Критерий успеха [допущение]:** −25% токенов на сопоставимых задачах без ухудшения
доли задач без возврата. **Провал:** экономия меньше 10% → главный столп не держит.

### MVP-2 — Второй проект и перенос (проверяем: переносим ли метод)
Завести намеренно другой по стеку проект, перенести ядро, зафиксировать что сломалось.
**Критерий:** ≥60% правил ядра применимы без изменений. **Провал:** <40% → «ядра» не
существует, есть только профили, и продукт другой.

### MVP-3 — Инбокс предложений (проверяем: доверяют ли обучению)
Детекторы 1–4, предложения с доказательствами.
**Критерий:** доля принятых предложений ≥30% и она не падает со временем.
**Провал:** <15% принятия → предложения шумят, механика не работает на этих объёмах.

### Что в MVP НЕ входит
Мультиагентная оркестрация, красивый борд, интеграция с Jira/Linear, командные роли,
биллинг, кросс-клиентское обучение, marketplace паков.

## 8. Развилка про текущий WorkTask (требует решения)

Текущий продукт — трекер: спринты, backlog, календарь, уведомления. Платформе нужны:
проекты с привязкой к репозиториям, прогоны, правила, предложения, метрики.

Честная оценка пересечения **[допущение, требует проверки по коду]**: переиспользуется
скорее инфраструктура (аутентификация, деплой, UI-кит, CI, накопленные инженерные
правила), чем доменная модель. Домен «спринт/доска/бэклог» платформе почти не нужен.

Три варианта:
1. **Платформа поверх текущего кода** — быстрый старт, риск тащить неподходящий домен.
2. **Новый продукт, WorkTask — первый клиент** — чище, дороже, но WorkTask остаётся
   живым полигоном (это ценно: у нас есть реальный brownfield с историей).
3. **WorkTask как витрина** — трекер остаётся, платформа встраивается сбоку.

Решение не принято. Оно зависит от результата MVP-0/MVP-1 — до появления цифр
выбирать преждевременно.

## 9. Ближайшие шаги (2 недели)

1. Первичная верификация ключевых цифр исследования (DX, Sonar, GitClear, звёзды).
2. Определить, что именно и как замеряем (MVP-0): источники сигналов, что считается
   «задачей», как считать rework.
3. Снять базовую линию на 5 реальных brownfield-задачах WorkTask.
4. На тех же задачах — эксперимент «delta-спека против текущего подхода».
5. 3–5 разговоров с агентствами/серийными разработчиками о мульти-проектной боли.

Кода не пишем до конца шага 3.
