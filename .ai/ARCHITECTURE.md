### Key Design Decisions

**ADR-001: ThreadLocal для пользовательского контекста**
- Решение: `UserContext` использует `ThreadLocal<UserContextData>`
- Причина: Простая передача user ID/email по стеку вызовов без явной параметризации
- Следствие: Необходимо очищать контекст после запроса (Spring фильтр)

**ADR-002: AOP-аннотации для транзакций**
- Решение: `@TransactionRequired` (REQUIRED) и `@TransactionMandatory` (MANDATORY)
- Причина: Явная документация транзакционных требований прямо в сигнатуре
- Следствие: В Unit-тестах AOP не применяется — тестируем логику, а не транзакции

**ADR-003: Liquibase для схемы БД**
- Решение: `ddl-auto: none`, Liquibase управляет всеми миграциями
- Причина: Воспроизводимость схемы, история изменений, безопасный rollback
- Миграции: `src/main/resources/db/changelog/changes/` (16 XML-файлов)

**ADR-004: Профили Spring**
- `local` — используется по умолчанию (`application-local.yml`), подключается к БД на VPS
- `prod` — переменные среды (`DB_URL`, `POSTGRES_USER`, `POSTGRES_PASSWORD`)
- CI — тесты запускают PostgreSQL как service container

## Voice Control Subsystem (Голосовое управление)

> Полный ADR и проектный документ — `.ai/VOICE_ARCHITECTURE.md`. Здесь — заголовочные решения.

Голос — **модальность ввода поверх существующих команд** (`workTechApi.*`), а не параллельная
бизнес‑логика. Конвейер: `SpeechProvider → VoiceContext → IntentResolver → SlotResolver →
ConfirmationGate → CommandExecutor → Feedback/Log`. Эволюция двух прежних итераций проекта:
удалённого командного микрофона (ТП‑22/57, реестр команд) и голосового ВВОДА (ТП‑88, шов
`IntentAnalyzer`).

**ADR‑005: Голос выполняет действия только через существующие мутации/сервисы**
- Решение: никаких прямых обращений в API/БД в обход UI‑слоя (`TaskPlacementService` и т.д.)
- Причина: единый источник бизнес‑логики и контракта фронт↔бэк, нет дублирования
- Следствие: набор голосовых возможностей ограничен существующим API

**ADR‑006: Реестр команд как механизм расширения (эволюция ТП‑22)**
- Решение: возможность = дескриптор `VoiceCommand` в реестре; распределённый `match()` заменён
  центральным `IntentResolver`
- Причина: масштабируемость без правки существующих компонентов; паттерн проверен прежним кодом
- Следствие: команда описывает себя (`description`/`examples`/`slots`) для резолвера

**ADR‑007: Распознавание намерения — на backend‑прокси, провайдер за интерфейсом (Strategy)**
- Решение: `POST /voice/resolve` + `IntentResolver`; провайдер через env (RuleBased/LLM)
- Причина: секреты только на сервере; работа с AI и без AI за одним швом; заменяемость
- Следствие: схема команд передаётся per‑request; нужен фолбэк RuleBased

**ADR‑008: LLM выбирает команду и заполняет слоты — исполняет система**
- Решение: резолвер → `commandId`+слоты; `SlotResolver` → ID; `Executor` → мутация
- Причина: анти‑галлюцинация (модель не трогает API/ID) — требование CLAUDE.md
- Следствие: нужен строгий `SlotResolver` и промпт «ничего не выдумывай»

**ADR‑009: ASR за `SpeechProvider`; дефолт — Web Speech (локально, без ключей)**
- Решение: `useSpeechRecognition` (ru‑RU, push‑to‑talk) как реализация интерфейса
- Причина: локальная обработка без выгрузки аудио; заменяемость на облачный ASR
- Следствие: ограничения браузера → graceful‑fallback к клавиатуре (TD‑016)

**ADR‑010: Push‑to‑talk в MVP; дуплекс/barge‑in/TTS — пост‑MVP**
- Решение: базовый режим «нажать → сказать → стоп»
- Причина: full‑duplex существенно сложнее и не нужен командной модели
- Следствие: разговорный режим — расширение `SpeechProvider`, не фундамент

## Meet Subsystem (Видеовстречи WorkTask Meet)

> Полный ADR и проектный документ — `.ai/MEET_ARCHITECTURE.md`. Здесь — заголовочные решения.

**ADR-011: Топология медиа — WebRTC full-mesh (P2P) с жёстким пределом 8 участников**
- Причина: реальные команды проекта 2–8 человек; mesh не требует медиасервера (границы владельца: затраты на SFU/managed)
- Следствие: предел `app.meet.max-participants` — единственный источник; путь масштабирования — зрелый SFU (LiveKit), собственный SFU запрещён

**ADR-012: Сигналинг — raw WebSocket в том же Spring Boot (`/work-task/ws/meet`)**
- Причина: поллинг 10–30с непригоден для SDP/ICE; STOMP избыточен для одного кастомного протокола
- Следствие: снимает вопрос «WebSocket/SSE для real-time» (ниже) — вводится общий WS-слой; миграция доски/уведомлений на него — будущие задачи

**ADR-013: Состояние встречи — backend, in-memory реестр; персистентна только комната (`meet_room`)**
- Причина: единственная нода приложения; присутствие эфемерно, комната — долгоживущая ссылка
- Следствие: при рестарте backend клиенты автоматически переподключаются

**ADR-014: Права встречи = членство в проекте; токен комнаты неугадываемый (SecureRandom 32 байта)**
- Причина: переиспользование модели прав продукта (`CheckerUtil`); ссылка не даёт доступа чужим
- Следствие: гостевой доступ без аккаунта — осознанно вне рамок (решение владельца)

**ADR-015: TURN-готовность через конфигурацию, секреты только в env**
- Причина: STUN покрывает типичные сети; TURN — инфраструктурное решение владельца
- Следствие: `MEET_TURN_URLS/USERNAME/CREDENTIAL` подключают TURN без изменения кода

## Observability (мониторинг клиентских ошибок, ТП-175)

**ADR-016: Мониторинг фронтенда — Sentry-совместимый SDK; backend мониторинга — конфигурация (DSN), не код**
- Решение: `@sentry/react` + self-hosted **GlitchTip** на VDS (`docker-compose.vds.yml`);
  ingest — nginx-локация `/api/<id>/(envelope|store|security)/` на основном 443,
  UI — `:8443` с тем же сертификатом. DSN приходит в сборку через `VITE_SENTRY_DSN`
  (пусто = SDK выключен). Source maps заливаются на сборке деплоя (`@sentry/vite-plugin`),
  release = git SHA.
- Причина: Sentry SaaS / self-hosted Sentry / GlitchTip принимают один протокол — выбор
  хостинга сводится к значению DSN и обратим; self-hosted дефолт оставляет данные в контуре.
- PII: **маскирование по умолчанию** (`beforeSend`-скрабинг: email/имена/токены/пароли,
  тела запросов не отправляются, user = только UUID). Ослабление — решение владельца.
- Алерты: GlitchTip webhook → `POST /work-task/api/v1/monitoring/alert?token=…` (секрет
  генерирует `infra/glitchtip/ensure-env.sh`) → уведомления MONITORING_ALERT участникам
  продуктового проекта в колокольчик WorkTask. Правила: новые ошибки (1/1м), всплеск (20/5м).
- Точки отправки: GlobalHandlers (`onerror`/`onunhandledrejection`) + `ErrorBoundary`
  (модалки/блоки) + `RouteErrorFallback` (крах роута).
- Bootstrap идемпотентен: `infra/glitchtip/bootstrap.py` (org/project/DSN/API-токен/алерты)
  выполняется пайплайном деплоя; секреты только на сервере.

## Phase 5: мульти-проектность и переносимые правила (модель данных, T-503)

> Основания: `.ai/MULTIPROJECT_AUDIT.md` (T-500 — что уже работает и где разрывы),
> `.ai/PHASE5_INVARIANTS.md` (T-502 — что обязано продолжать работать и правила миграций),
> `.ai/RULES_TAXONOMY.md` (уровни правил), `.ai/PLATFORM_PRODUCT_MAP.md` (продуктовая рамка).
>
> **Схема спроектирована, реализация не начата.** Все таблицы аддитивны: существующий
> проект работает без единой записи в них (инвариант I-03).

### Сущности

**`repo_binding`** — привязка проекта к репозиторию.

| Поле | Тип | Примечание |
|---|---|---|
| `id` | String (UUID) | как у 16 из 20 существующих сущностей |
| `project_id` | FK → `project` | `nullable = false` |
| `provider` | String | `github` \| `gitlab` \| … |
| `url` | String | адрес репозитория |
| `default_branch` | String | ветка по умолчанию |

**`rule_set`** — именованный набор правил, единица переноса между проектами.

| Поле | Тип | Примечание |
|---|---|---|
| `id` | String (UUID) | |
| `owner_user_id` | FK → `users` | владелец набора |
| `project_id` | FK → `project`, **nullable** | `null` = набор уровня пользователя («общие»), иначе — проектный |
| `name`, `description` | String | |
| `version` | int | для осознанного обновления скопированных наборов |

**`rule`** — правило. Поля следуют реестру `PROJECT_RULES.md`, приведённому к табличному виду
задачей T-107: перенос механический, а не переосмысление.

| Поле | Тип | Примечание |
|---|---|---|
| `id` | String (UUID) | |
| `rule_set_id` | FK → `rule_set` | `nullable = false` |
| `code` | String | `K-27`, `W-03`, `F-01` — человекочитаемый идентификатор |
| `level` | enum | `CORE` \| `PACK` \| `PROFILE` (уровни `RULES_TAXONOMY`) |
| `kind` | enum | `PRINCIPLE` \| `GATE` \| `PROCEDURE` \| `PROHIBITION` |
| `strength` | enum | `MUST` \| `SHOULD` |
| `trigger` | String | условие загрузки (`всегда`, `багфикс`, `новая зависимость`…) |
| `verification` | enum | `AUTO` \| `SEMI` \| `MANUAL` |
| `body` | text | формулировка |
| `source_rule_id` | String, **nullable** | провенанс: из какого правила скопировано |
| `system_rule` | boolean | закреплённое, по аналогии с `TaskStatus.system_status` |

**`process_step`** — этап процесса задачи, принадлежит проекту и переносится вместе с
правилами.

| Поле | Тип | Примечание |
|---|---|---|
| `id` | String (UUID) | |
| `project_id` | FK → `project` | `nullable = false` |
| `code`, `name` | String | `A0`, `A1`, `A2`, `D`, `I`, `V` |
| `position` | int | порядок |
| `required_from_size` | enum, **nullable** | с какого размера задачи этап обязателен (T-516) |

Связь задачи с этапом (`task.current_process_step_id`) — **nullable**, вводится по правилу
двухшагового ввода (`PHASE5_INVARIANTS` §4, п. 5): 184 существующие задачи не обязаны иметь
этап.

### ADR

**ADR-017: Правила в БД — библиотека и редактор, но НЕ источник, который читает агент**
- Причина: `PLATFORM_PRODUCT_MAP §3` помещает `Rule` в облако и одновременно требует «в
  репозитории — суть продукта», а T-514 требует, чтобы правила работали **без подключения к
  WorkTask**. Двусмысленность разрешается разделением ролей: БД хранит правила, чтобы их
  можно было переносить, версионировать и предлагать изменения; агент читает **файлы
  репозитория** (`CLAUDE.md`, `.ai/PROJECT_RULES.md`, сгенерированный `AGENTS.md`).
- Следствие: экспорт (T-514) материализует правила в репозиторий, и рабочей является
  материализованная копия. Правила переживают откат кода вместе с кодом, видны в PR и
  работают при недоступной платформе. БД — не единственный источник истины, а редактор.

**ADR-018: Уровень правила — поле, а не отдельная сущность; «общий» набор = `rule_set` без проекта**
- Причина: уровни (`CORE`/`PACK`/`PROFILE`) — атрибут правила, а не отдельная таблица;
  вводить иерархию наборов ради трёх значений — усложнение без пользы (K-38, YAGNI). Nullable
  `project_id` вместо полиморфной связи — прецедент есть (`Notification.project_id`).
- Следствие: «общие правила пользователя» и «правила проекта» — одна таблица, один CRUD,
  один экран. Промоушен правила между уровнями — смена поля, не перенос между сущностями.

**ADR-019: Копирование правил при создании проекта — расширение существующего механизма**
- Причина: механизм «при создании проекта наполнить набор» уже существует и работает —
  `ProjectsService.createProject` вызывает `createDefaultStatuses` (из enum `StatusName`) и
  `createDefaultSprint`. Новая парадигма не нужна, нужен ещё один такой шаг (K-38,
  consistency over novelty).
- Следствие: `createRuleSetForProject(project, donor)` встраивается рядом, в ту же
  транзакцию. **Копия независима** от источника (правки в доноре не текут в проект), но
  происхождение хранится в `rule.source_rule_id`, а `rule_set.version` позволяет осознанно
  обновиться. Это удовлетворяет требованию T-512 и правилу провенанса `PLATFORM_PRODUCT_MAP §5`.

**ADR-020: `repo_binding` — отдельная таблица, а не колонки в `project`**
- Причина: WorkHelper сам монорепо (`backend/`, `frontend/`), и проект может быть связан с
  несколькими репозиториями. Отдельная таблица поддерживает N без переделки и следует
  существующему паттерну «набор, принадлежащий проекту» (`TaskStatus`, `Sprint` — тоже
  отдельные таблицы с FK на `project`).
- Следствие: миграция строго аддитивна, существующие проекты живут без привязки (I-03).

**ADR-021: Процесс задачи принадлежит проекту и копируется вместе с правилами**
- Причина: процесс — такая же переносимая часть метода, как правила; держать его отдельным
  механизмом означало бы два способа переноса одного и того же.
- Следствие: `process_step` копируется тем же шагом создания проекта (ADR-019). Связь задачи
  с этапом nullable, обязательность вводится вторым шагом после бэкофилла
  (`PHASE5_INVARIANTS` §4, п. 5).

**ADR-022: Реализация фазы не начинается до снятия базовой линии (MVP-0)**
- Причина: `PLATFORM_PRODUCT_MAP §7` требует инструментирования до изменений процесса и
  прямо фиксирует «кода не пишем до конца шага 3». Схема выше спроектирована, чтобы решение
  было принято осознанно, но её ценность (экономия контекста, переносимость) пока **не
  измерена**. Строить таблицы под недоказанную ценность — тот же класс ошибки, что правила,
  описывающие несуществующие механизмы (T-106).
- Следствие: T-510…T-519 остаются `NOT_STARTED` до появления цифр. Исключение —
  задачи, ценность которых доказана независимо от платформы: T-518 (закрывает разрывы
  G-1…G-9 из T-500) и TD-028/TD-029.

### Доставка правил агенту (T-504)

Основание: `.ai/RULES_DELIVERY_AUDIT.md` (T-501) — правила доходят пятью каналами, и
файловый не самый объёмный.

**ADR-023: `AGENTS.md` — генерируемый файл; дублирование допустимо, потому что машинное**
- Причина: из семи разделов `CLAUDE.md` специфичен для Claude Code только «Старт сессии»
  (порядок загрузки — свойство конкретного харнесса). Остальные шесть — ядро, конвейер
  запроса, продукт, уроки, деплой, профиль — универсальны, и любому другому агенту нужны
  они же. Значит `AGENTS.md` неизбежно повторит ~15 КБ. Отказаться от него нельзя: без него
  весь корпус привязан к одному вендору (T-501 §4).
- Следствие: дубль разрешён **при двух условиях** — он порождается машиной и направление
  строго одностороннее (`.ai/PROJECT_RULES.md` + `CLAUDE.md` → `AGENTS.md`), файл помечен
  «сгенерирован, не редактировать» и коммитится в репозиторий. Именно это отличает его от
  дубля, снятого T-107: **тот был рукописным и потому разошёлся** (два противоречия, T-106).
  Машинный односторонний дубль разойтись не может по построению. Правка `AGENTS.md` руками —
  дефект, а не изменение правил.

**ADR-024: MCP-сервер отвечает за задачи и телеметрию, но НЕ за правила**
- Причина: после ADR-017 и ADR-023 правила уже доезжают файлами и работают без сети.
  Отдавать их ещё и по MCP значило бы завести второй источник того же содержания — ровно
  та ошибка, которую сняли T-107 и ADR-023.
- Следствие: контракт T-517 сужается до того, чего в файлах нет и быть не может: получить
  задачу и её контекст, вернуть статус и результат, отправить сигналы и метрики прогона
  (`Run`, `Signal` из `PLATFORM_PRODUCT_MAP §3`). Правила остаются файлами репозитория.

**ADR-025: Граница ответственности и деградация без платформы**
- Причина: продажа и эксплуатация упираются в вопрос «что перестанет работать, если
  WorkTask недоступен» (`PLATFORM_PRODUCT_MAP §1`).
- Следствие — явное разделение:

| Слой | Что хранит | Работает без платформы |
|---|---|---|
| Репозиторий | правила, профиль проекта, уроки, ADR, сгенерированный `AGENTS.md` | **да** — это файлы под git |
| Платформа (WorkTask) | задачи, статусы, метрики прогонов, предложения правил | нет |
| Агент | исполнение | **да**, в режиме «правила есть, задача поставлена человеком» |

  То есть при недоступной платформе теряется постановка задач и телеметрия, но **не метод
  работы**. Это и есть проверяемый критерий T-514 «работает без подключения к WorkTask».

**ADR-026: «Текущий проект» — это адрес страницы, а серверное поле — только точка входа (T-518)**
- Причина: `GET /projects/{id}` писал `user.last_project_id`, то есть чтение переключало
  рабочий контекст глобально. Из одного этого решения вытекали G-1…G-4 аудита T-500: доску
  нельзя передать ссылкой, две вкладки с разными проектами невозможны, взгляд в бэклог
  чужого проекта уводил за собой доску.
- Решение: проект живёт в URL (`/project/$projectId/board` рядом с уже существующими
  `backlog`/`sprint`/`calendar`). `last_project_id` остаётся, но меняется **только** явным
  `PUT /projects/{id}/last` и отвечает на один вопрос — «где открыть `/main` и следующий
  вход».
- Шов на фронтенде — не router-хук, а стор вкладки (`currentProjectStore`): `useProjectData`
  вызывают в том числе компоненты NiceModal-модалок, которые монтируются вне Router-контекста,
  и router-хук уронил бы дерево (**R-02**, прод-инцидент ТП-172). Маршруты кладут `projectId`
  в стор, потребители читают оттуда.
- Следствия: доска стала deep-link'абельной; вкладки независимы; эндпоинт доски получил
  `projectId` и явную проверку членства (раньше проект приходил из доверенного серверного
  поля). `/main` сохранён как редирект — на него ведут 14 мест приложения.
- Отложено сознательно: `/task/$code` по-прежнему резолвится в текущем проекте (G-4) — это
  связано с уникальностью `project.code` (G-5) и делается вместе с ней.

### Миграции фазы

Обязательны правила `PHASE5_INVARIANTS §4`. Эталон, которому следуют все миграции фазы, уже
есть в репозитории — `20250703-add-backlog-column-to-projects.xml`: аддитивно, идемпотентно
(`NOT EXISTS`), с явным `<rollback/>` и комментарием-обоснованием. Новые changeSet
подключаются автоматически (`includeAll path="db/changelog/changes"`).

Единственная **не-аддитивная** миграция в планах — уникальность `project.code` (G-5 из
T-500). Выполнять её нужно, пока проект один и конфликтов нет.
